# Contentful House Style Patterns

Contentful-specific documentation patterns observed across Applied AI Solutions (AIS), the broader ECO product line, and other Contentful engineering teams. Loaded by `doc-review` and other doc-relevant skills. For doc type definitions and structural templates, see doc-types.md §1–6. For voice rules that apply across all doc types, see voice-and-structure.md.

## Evals Discipline (Load-Bearing Differentiator)

AI features in RFCs require an evals plan. AI-generated internal artifacts require a human verification step before merge. This is not a best-practice suggestion — it is a director-level mandate stated as "full stop."

**The mandate:** Mike Kivisto's February 2026 All Hands ([slides](https://docs.google.com/presentation/d/1qb1NNCIjIakodLN8YGZrckM8ilMeiTCDlFucIqdkpHM)): "If an LLM is part of the feature you are shipping you need to use AI Evals. Full stop." The April 10 follow-up ([prd-ecosystem-chat](https://contentful.slack.com/archives/C07RKUD0W20/p1775840584257459)) listed evals as a present-tense peer item with writing specs and building agents. The May 6 thread ([prd-ecosystem-chat](https://contentful.slack.com/archives/C07RKUD0W20/p1778092500679499)) extended the mandate to AI-generated internal artifacts: "What David did is probably a great jumpstart but from now until....someday(?)....we need to verify what is being output." The "someday(?)" framing explicitly rejects the idea that human verification is temporary.

**What the mandate requires in RFCs:** An RFC proposing an AI-powered feature must address:

1. **Eval type selection** — Task-Specific, LLM-as-Judge (with explicit judging-model risk acknowledgment), Human, or Regression Evals.
2. **Regression eval plan** — required whenever prompts change, models swap, or tools/agents are added.
3. **HITL considerations** — identify where human review gates are applied; HITL is a peer line item with evals.
4. **No evals deferral** — "we'll add evals in a future sprint" is a direct contradiction of the mandate. The Finder flags it.

**As an authoring rule (not just a review check):** an AI-feature RFC must include an eval/success-metrics plan as a first-class section — how the feature is measured and what "passing" means to graduate it (Aakash Gupta: "what constitutes passing metrics to graduate the experiment"; Hamel Husain: evaluation is "the most important part of the whole system"). Two companions observed in AIS practice belong with it:
- **Cost model** — for LLM features, the per-invocation and aggregate COGS, including any sampling multiplier.
- **Rollback criteria** — the operational condition under which the feature is turned off (the webhook-smoothing RFC's dedicated "Rollback Plan" is the local exemplar).

**What the mandate requires for AI-generated artifacts:** AGENTS.md, CLAUDE.md, ARCHITECTURE.md, and other golden context files generated by an AI agent must not be merged without a human review pass. Automated generation is a valid starting point; human verification before merge is non-optional.

**Finder checks:** (1) Any RFC containing `LLM`, `AI`, `model`, `agent`, `prompt`, `embedding` — does it have an evals section? (2) Any AI feature RFC that defers evals — flag, cite mandate. (3) Any AI-generated context file submitted without a verification step.

## ADR Filename Convention (with Scope Awareness)

Tundra, ECO-space, and ExO repos use date-based ADR filenames: `YYYY-MM-DD-title.md`. The SDK team uses sequential filenames: `0001-title.md`. Neither convention is org-mandated. The conventions coexist; the right convention depends on the repo's team context.

**Tundra/ECO/ExO (date-based):** `YYYY-MM-DD-title-with-dashes.md`, stored in `docs/ADRs/`. A sequential filename in a Tundra/ECO/ExO repo is a deviation — flag it.

**SDK team (sequential):** `0001-title-with-dashes.md` per Nygard and MADR 4.0. A date-based filename in an SDK repo is a deviation — flag it.

Detection: Tundra/ECO correct: `^\d{4}-\d{2}-\d{2}-`. Sequential in a Tundra repo (flag): `^\d{4}-[^0-9]`. Requires repo-context. Cross-reference: doc-types.md §4.

**Superseded ADR pattern:** Retained (never deleted) with bidirectional links — new ADR references what it supersedes; old ADR is updated to point to its replacement.

## Owner Pointers Go to Teams or CODEOWNERS, Never Individual Names

Shipped docs — RFCs, AGENTS.md, ARCHITECTURE.md, ADRs, READMEs, PRDs, design docs — use team names, functional roles, or CODEOWNERS paths as owner pointers. Individual names go stale and commit people to roles they did not agree to.

**What belongs:**
- `Owner: Applied AI Solutions` in a Risks & Mitigations table
- `Owner: Marketplace + Extensibility` for a cross-team risk (team names, not individuals)
- `CODEOWNERS: /packages/app-framework/ @contentful/tundra`
- `Contact: #ext-tundra-engineering` (Slack channel alias)

**What does not belong:**
- `Owner: <First Last>` literal personal-name pattern in a milestone table (any individual, not a team or CODEOWNERS path)
- `Reach out to <First Last> with questions` in an AGENTS.md or README — direct individual-name pointer instead of a team alias or CODEOWNERS reference
- `Maintainer: @<firstname>.<lastname>` handle in a README owner field — handles are individual names with extra steps

**Scope:** This rule applies to all shipped docs. Internal planning scratch (GAPS.md, decisions.md, personal notes in `projects/active/`) is exempt — individual names are fine in private working documents. The question is always: will this doc be visible to other engineers who are not party to the planning conversation?

**Doc-review lens:** Lens 1 (Memory-encoded rules). Finder pattern: `(Reach out to|Contact|Owner:|Maintainer:)\s+[A-Z][a-z]+\s+[A-Z][a-z]+` where the match is a personal name rather than a team alias or CODEOWNERS path. Mike Kivisto is the only spec-named individual exception in doc-patterns content — see §Evals discipline.

## AGENTS.md as Evergreen State — Bloat, Misplaced, OK Taxonomy

The `contentful-update-agents-md` skill in `contentful/agents-kit` enforces a three-tag classification for AGENTS.md content:

- **`ok`** — content that belongs: non-discoverable, high-impact constraints; guardrails that cannot be inferred from code, config, or tooling; safety rules; ask-first boundaries.
- **`bloat`** — content that should be removed: anything discoverable from `package.json`, `tsconfig.json`, lint configs, or directory structure. Includes: `npm run` script enumerations, setup commands, testing taxonomy, file/module naming conventions already enforced by linters, build commands already in package.json scripts.
- **`misplaced`** — content that belongs somewhere else: state management decision trees, multi-line code examples, dependency/build/lint preferences (→ skills and hooks), procedural instructions (→ skill files or README).

**The litmus test:** "If removing this line would cause an agent to violate a repo constraint it has no other way to learn, the line belongs. Otherwise it does not."

**Size rule:** Root AGENTS.md under ~100 lines. Bloated context files reduce agent task success rates and increase inference cost (per contentful-update-agents-md conventions.md). This is a content discipline, not a soft guideline.

**Deliberate divergence from community spec:** The community spec at [agents.md](https://agents.md/) lists setup/build commands as a popular choice. Contentful's doctrine explicitly rejects them — they belong in README and package.json.

**Skeleton structure (in order):** (1) Brief intro, 1–3 lines; (2) Guardrails: Do/Don't bullets or Anti-Patterns and Invariants; (3) Commands: only if non-obvious; (4) Safety/Permissions: never-do and ask-before-doing rules.

CLAUDE.md is the internal-only counterpart — carries workflow, team context, Jira keys, and Slack channels. AGENTS.md ships to both public and private repos; CLAUDE.md must never be proposed for a public repo.

## AGREE / INPUT / CONSULT Audience-Table Convention

RFC audience tables use three roles:

- **AGREE** — veto power; must be as few as possible. Maps to the Contentful RAPID Agree role.
- **INPUT** — provides data and domain context; no veto. Maps to RAPID's Input role.
- **CONSULT** — advisory awareness only; no veto, no blocking responsibility. AIS extension beyond the org template's AGREE/INPUT pair.

AGREE and INPUT borrow directly from RAPID vocabulary. CONSULT is an AIS addition. MADR 4.0's frontmatter (`decision-makers`, `consulted`, `informed`) independently maps to the same taxonomy — structural alignment across two sources.

**When CONSULT absence is flaggable:** An RFC with cross-boundary implications (shared infra dependency, cross-team coordination gate) but only AGREE and INPUT rows — flag the missing CONSULT row as a coverage gap. This is an AIS-convention issue, not a violation of the org template.

**Audience table column structure:** Role | Individual(s) or Team(s) | Detail (what each reviewer is being asked to validate). The Detail column is required — an audience table without it does not communicate reviewer scope.

## Citation Conventions in Jira and Confluence Markdown

Bare URLs do not auto-link in Jira ADF (`contentFormat: "markdown"`). Always use `[text](url)` in Jira issue descriptions, comments, and Confluence markdown bodies.

**Additional ADF constraints:**
- No inline `` `code` `` inside link text — the ADF parser drops code spans in links. Write `[contentful-update-agents-md skill](url)` not `` [`contentful-update-agents-md`](url) ``.
- No `- [ ]` checkboxes in Jira markdown — the ADF converter escapes them to `\[ \]`. Use numbered or plain bullet lists for actionable items.

These constraints are Jira/Confluence-specific. GitHub PR descriptions and skill files are more forgiving, but `[text](url)` is preferred everywhere for consistency.

**Doc-review lens:** Lens 4 (Voice/writing-style). See failure-modes.md §Lens 4 for the grep pattern. Voice-and-structure.md §Citation conventions covers the broader rule.
