# OWASP Mapping — Tundra Stack

Maps OWASP Top 10 (2025) and OWASP API Security Top 10 (2023) entries to the Tundra stack (TypeScript/Node, AWS, Cloudflare, Contentful CMA, Mastra). Each entry references the threat category vocabulary from `threat-categories.md`.

---

## Standard OWASP Top 10 (2025)

---

## OWASP-A01: Broken Access Control

**Maps to threat category:** Authorization

**In the Tundra stack:** APS-backed authorization fails silently — a misconfigured or regressed policy produces a 403 with no fallback, breaking apps that depend on implicit permissions (e.g., "app reads the AppActionCall it created") without error. Per-object authorization must be checked at every data retrieval; route-level checks alone are insufficient when Contentful CMA IDs are user-supplied.

**Code patterns to flag:**
- Object returned by ID without a preceding authorization check against the caller's identity/scope
- APS `lib/stores/policies/app/` modified without integration tests covering the affected access pattern
- `subjectId` passed to APS without asserting expected string format (exact-match prefix mismatch silently denies)

**Mitigations available:**
- Deny by default for all non-public resources; enforce authorization at the object-retrieval layer, not just route entry
- Integration-test every APS policy change against the full set of subject formats and access patterns it affects

**Source:** OWASP Top 10 (2025)

---

## OWASP-A02: Security Misconfiguration

**Maps to threat category:** Blast Radius / Data Exposure

**In the Tundra stack:** Cloudflare worker configuration, CORS rules on app proxy endpoints, and Terraform-managed AWS resource settings are all "configuration as code." Overly permissive CORS on authenticated extensibility-api routes, debug/metrics endpoints left enabled in Cloudflare deployments, or AWS security groups defaulting to allow-all are the Tundra-specific manifestations. Verbose error responses from the app hosting layer are also a misconfiguration concern (covered under OWASP-A08 in API context).

**Code patterns to flag:**
- CORS header set to `*` on an authenticated extensibility-api or app-proxy route
- Terraform security group with `0.0.0.0/0` ingress on a service not requiring internet exposure
- Debug or health-check endpoints without authentication in production Cloudflare Worker routes

**Mitigations available:**
- Terraform security groups start deny-all; only required ports/sources opened with explicit `cidr_blocks` lists in IaC
- CORS `Access-Control-Allow-Origin` enumerates specific origins in `wrangler.toml` or the CORS middleware config — `*` on an authenticated route is a hard fail regardless of other controls
- Cloudflare Worker routes have `wrangler` env-var validation; debug/`/health`/`/metrics` endpoints either authenticated or absent in production deployments

**Source:** OWASP Top 10 (2025)

## OWASP-A03: Software Supply Chain Failures

**Maps to threat category:** Dependency / Supply Chain

**In the Tundra stack:** Tundra runs multiple Node services with `@contentful/service-*` packages that pin vulnerable transitive deps (axios, fast-xml-parser, follow-redirects, undici). Typosquatting artifacts from mistyped `npm i` commands have been found in production `package.json` files. `npm overrides` blocks used to force-patch transitive deps are invisible to Dependabot and exempt from future CVE alerts.

**Code patterns to flag:**
- `package.json` listing single-char (`i`, `n`) or bare CLI-word (`npm`, `install`) packages — typosquatting artifacts
- `package.json` `overrides` block without a dated inline comment and companion cleanup ticket
- CI/CD `npm install` rather than `npm ci` — lockfile not respected; lock can be silently overwritten
- Absence of `.github/dependabot.yml` or `renovate.json` in a production repo — no automated CVE alerts

**Mitigations available:**
- `npm ci` in all CI/CD; commit `package-lock.json`; `min-release-age=7d` in `.npmrc`
- `npm audit --audit-level=high` + `npm audit signatures` as CI gates
- `actions/dependency-review-action` as required status check; Wiz SBOM for deployed runtime CVE triage
- Renovate (org-standard) for automated dependency updates; do not run Renovate and Dependabot simultaneously

**Source:** OWASP Top 10 (2025)

## OWASP-A04: Cryptographic Failures

**Maps to threat category:** Secrets & Credentials

**In the Tundra stack:** Tundra uses AWS KMS and Secrets Manager for key management; the risk surface is in code generated by AI tools (Veracode: 88% of AI-generated cryptographic code uses deprecated algorithms or hardcoded IVs) and in any new serverless component that handles token signing or encryption. Cloudflare request signing for the Functions API uses a multi-layer secrets model (1Password → Secrets Manager → GitHub Environment Secrets) — deviations from this pattern are the failure signal.

**Code patterns to flag:**
- Use of `md5`, `sha1`, or `des` in any cryptographic operation (not checksumming)
- Hardcoded initialization vector or key in encryption code
- Secrets passed as plaintext in environment variables outside the approved Secrets Manager / vault orb path

**Mitigations available:**
- Approved secrets pattern: 1Password → AWS Secrets Manager (Terraform-provisioned, `service_tag` + `namespace_types` scoped) → CircleCI vault orb
- AWS KMS for key management; never commit cryptographic keys to source

**Source:** OWASP Top 10 (2025)

## OWASP-A05: Injection

**Maps to threat category:** Input Validation

**In the Tundra stack:** The injection surface in Tundra is broader than SQL — it includes: (1) webhook transformation expressions that process user-supplied payloads (confirmed unbound recursive execution in INC-350); (2) AI agent prompts that incorporate user-controlled CMS content, Jira bodies, or GitHub PR descriptions (indirect prompt injection); (3) ORM/Prisma query construction in TypeScript services. XSS is the residual risk in the Contentful web app where app iframe content can attempt to inject into the parent frame.

**Code patterns to flag:**
- String interpolation in ORM/SQL calls instead of parameter binding
- Agent system prompt that reads user-controlled content (CMS entries, Jira bodies) without an "ignore embedded instructions" directive
- Webhook transformation code processing user-supplied expressions without recursion depth or CPU time limits
- `invoke_ai_action` returning `nextStepsGuidance` as a directive string rather than optional/suggestive language

**Mitigations available:**
- Parameterized queries only; no string interpolation in any query construction
- Explicit anti-injection instruction in every agent system prompt that reads user-controlled content
- Recursion depth and CPU time bounds on all user-supplied transformation expressions

**Source:** OWASP Top 10 (2025)

## OWASP-A06: Insecure Design

**Maps to threat category:** Authorization / Blast Radius

**In the Tundra stack:** APS's exact-match subject prefix lookup is a design-level property — a consumer that constructs the wrong subject format is denied silently with no fallback, which is correct behavior when it works but invisible when it fails. Multi-tenant token caching that omits `userId` from the composite key is an insecure design decision (not a bug) — it collapses tenant isolation by construction.

**Code patterns to flag:**
- `TokenContext` constructed without `userId` on a server-side multi-tenant backend
- Authorization logic implemented as post-retrieval filter rather than as a query predicate (retrieves all records, then filters — IDOR exposure window exists)
- Org-scoped endpoints that fan out N×M downstream calls without per-tenant rate limiting in the design

**Mitigations available:**
- `userId#spaceId#environmentId#appDefinitionId` composite key as the canonical multi-tenant isolation pattern
- Threat model produced during Security Review Process Phase 3b; apply Synopsys attack-tree methodology to new architectural decisions

**Source:** OWASP Top 10 (2025)

## OWASP-A07: Authentication Failures

**Maps to threat category:** Authentication

**In the Tundra stack:** Tundra's auth surface covers: OAuth callback `state` validation in app OAuth flows, JWT `aud` binding in the APS token exchange, and session handling in the app proxy. INC-984 (2026-01) confirmed that a missing OAuth `state` return caused production OAuth flows to fail — while the manifestation was a functional failure rather than a CSRF exploit, the CSRF attack path is structurally present when `state` is not validated. FastMCP GHSA-5h2m-4q8j-pqpj (2026-03) demonstrated that hardcoding JWT `aud` to a base URL rather than the `resource` parameter enables cross-server token reuse.

**Code patterns to flag:**
- OAuth callback handler that does not validate the `state` parameter, or allows it to be omitted
- JWT issuance code that hardcodes `audience` to a base URL rather than binding to the `resource` parameter
- New AI platform API endpoint that does not explicitly call an authentication/session validation function before processing

**Mitigations available:**
- Validate `state` on every OAuth callback; bind JWT `aud` to the `resource` parameter from the authorization request
- Rate-limit middleware on all auth endpoints; token expiry set on every newly issued credential
- Security Review Process Phase 3 explicitly audits: "long-lived tokens, expirations, lifecycle"

**Source:** OWASP Top 10 (2025)

## OWASP-A08: Software or Data Integrity Failures

**Maps to threat category:** Dependency / Supply Chain

**In the Tundra stack:** The integrity failure surface in Tundra is primarily CI/CD pipeline integrity and CDN-loaded asset integrity. GitHub Actions workflows that process untrusted input (issue titles, PR bodies) and grant AI agents shell access are the supply-chain integrity risk (see Cline "Clinejection" 2026-02). CDN-loaded scripts without Subresource Integrity (SRI) hashes are a data integrity failure. Unsigned releases from CI pipelines with broad publish credentials are a software integrity risk.

**Code patterns to flag:**
- GitHub Actions workflow with `pull_request_target` or `issues` trigger + AI agent shell access + untrusted input interpolation into the prompt
- `<script src="https://cdn.example.com/lib.js">` tag without `integrity="sha384-..."` and `crossorigin="anonymous"` attributes
- Actions workflow with no `permissions:` block (defaults to write-all in many org configs)

**Mitigations available:**
- Require `actions/dependency-review-action` as a status check; pin all Actions to exact SHAs
- SRI hashes on all CDN-loaded scripts and stylesheets; generate via `openssl dgst -sha384`

**Source:** OWASP Top 10 (2025)

## OWASP-A09: Security Logging and Alerting Failures

**Maps to threat category:** Blast Radius / Data Exposure

**In the Tundra stack:** INC-1276 (2026-05) and INC-350 (2025-05) were both prolonged because alerting did not exist on authorization-error rates, queue depth, or pod CPU throttling. The 30-hour detection gap in INC-633 (2025-09) was directly attributable to no authorization-error-rate monitoring on the APS access path. Logging of security-relevant events (auth denials, high-value operations, token issuance) must flow to the central logging solution per Contentful's Secure Development Policy.

**Code patterns to flag:**
- Authorization denial events not emitted as structured log events (or emitted without org/space/app context)
- Error handler that logs `error.stack` or internal paths (risk of sensitive data in logs) — see also Data Exposure category
- No alerting threshold on queue depth or consumer pod CPU for services processing webhook transformation expressions

**Mitigations available:**
- Log all authorization decisions (grant and deny) with caller identity, resource ID, and timestamp
- Centralized log management per Contentful Secure Development Policy; alert thresholds for authorization-error-rate spikes

**Source:** OWASP Top 10 (2025)

## OWASP-A10: Mishandling of Exceptional Conditions

**Maps to threat category:** Blast Radius

**In the Tundra stack:** Unhandled exceptional conditions in Tundra have caused multi-tenant availability failures. INC-350's unbound recursive loop in webhook transformation logic is a failure to handle the "expression depth exceeded" exceptional condition — there was no recursion depth limit and no error-path that terminated the execution. INC-1276's `AppDefinitionLoader` had no error handling for 5xx responses, causing silent blank-page rendering and masking the cascading failure. Partial transaction failures in multi-step APS token flows (token issued but cache write fails) leave the system in an inconsistent state.

**Code patterns to flag:**
- Webhook transformation or expression-evaluation code with no maximum recursion depth limit or CPU timeout
- Error handler that catches all exceptions and returns `null` or silently continues rather than failing closed
- Multi-step token issuance without rollback logic if any step fails

**Mitigations available:**
- Global exception handler with structured error logging; all multi-step transactions fail closed with complete rollback on error
- Per-tenant rate limiting and circuit breaking on org-scoped fan-out endpoints
- Resource quotas (recursion depth, CPU time) on all user-supplied expression evaluation

**Source:** OWASP Top 10 (2025)

## OWASP API Security Top 10 (2023)

---

## OWASP-API01: Broken Object Level Authorization (BOLA / IDOR)

**Maps to threat category:** Authorization

**In the Tundra stack:** The Tundra multi-tenant API has CMA object IDs (space IDs, environment IDs, app definition IDs, entry IDs) that are caller-supplied in route parameters. If the service returns the object without verifying the caller has access to that specific ID — relying instead on a route-level auth check — it is an IDOR. The APS delegation flow is the primary mitigation: `TokenManager.getToken()` accepts the caller's session token as the trust anchor, and the composite cache key `userId#spaceId#environmentId#appDefinitionId` enforces that a token fetched for one user cannot be served to another.

**Code patterns to flag:**
- Object retrieval by user-supplied ID without a per-object APS authorization check after retrieval
- Accessing nested resources (e.g., `/spaces/{id}/environments/{envId}`) where only the top-level object is access-checked
- `TokenContext` constructed server-side with a hardcoded or system-derived `userId` rather than the caller's session identity

**Mitigations available:**
- Authorization check on every function that retrieves a data source using a caller-supplied identifier
- `userId#spaceId#environmentId#appDefinitionId` composite key in the token cache — omitting `userId` collapses BOLA protection

**Source:** OWASP API Security Top 10 (2023)

## OWASP-API02: Broken Authentication

**Maps to threat category:** Authentication

**In the Tundra stack:** The token-based, stateless API context exposes JWT-validation gaps: expired tokens accepted, unexpected claims not rejected, API keys leaked via error messages or URL parameters. The app OAuth callback `state` validation failure (INC-984) is the Tundra-specific example.

**Code patterns to flag:**
- JWT validation that does not check `exp`, `aud`, or `iss` claims
- API key or bearer token logged or included in error response body
- Credential stuffing or brute-force not rate-limited on auth endpoints

**Mitigations available:**
- Reject tokens with unexpected or missing claims; enforce expiry on every newly issued credential
- Rate limiting and lockout on all authentication endpoints
- Use standardized protocols (OAuth 2.0, OpenID Connect); no custom token schemes

**Source:** OWASP API Security Top 10 (2023)

---

## OWASP-API03: Broken Object Property Level Authorization

**Maps to threat category:** Authorization / Data Exposure

**In the Tundra stack:** The extensibility-api response serialization and the app proxy are the surfaces where full model objects can be returned to callers who should only see a subset of fields. Mass assignment via PATCH on app installation or app definition objects is the writable-field risk — if the API accepts arbitrary JSON properties and maps them to the model, callers can set fields (e.g., `isAdmin`, `orgScoped`) that should be system-controlled.

**Code patterns to flag:**
- API response serializing the full TypeScript/ORM model object rather than an explicit DTO with allowlisted fields
- PATCH handler that spreads the request body directly onto the model (`Object.assign(entity, req.body)`) without an explicit allowlist of writable properties
- Response including internal flags, system-managed fields, or cross-tenant metadata alongside caller-visible fields

**Mitigations available:**
- Allowlist-based serialization: return only fields the caller's role may see or modify
- Separate input and output types; explicitly define which properties are user-writable in PATCH handlers

**Source:** OWASP API Security Top 10 (2023)

## OWASP-API04: Unrestricted Resource Consumption

**Maps to threat category:** Blast Radius

**In the Tundra stack:** This is the INC-1276 failure mode: one heavy org consuming enough shared-shard resources to degrade availability for all other tenants. The app installation fan-out (one API call → N×M DynamoDB queries) without per-tenant rate limiting or circuit breaking is the canonical pattern. Webhook processing without payload size or expression depth limits is the INC-350 pattern.

**Code patterns to flag:**
- Org-scoped API endpoint fanning out N×M downstream calls without per-tenant rate limiting
- Missing payload size limit on webhook body or app action call parameters
- GraphQL query or equivalent without depth or complexity limits

**Mitigations available:**
- Per-tenant rate limiting and circuit breaking on all org-scoped fan-out endpoints
- Payload size limits and timeout values enforced at the API gateway and application layer

**Source:** OWASP API Security Top 10 (2023)

---

## OWASP-API05: Broken Function Level Authorization

**Maps to threat category:** Authorization

**In the Tundra stack:** Administrative and internal endpoints in the extensibility-api (e.g., app definition management, organization-level operations) must be guarded with explicit privilege checks, not just authenticated. The APS policy layer handles this for app-level actions; the risk is in any new endpoint added to the AI platform or agent infrastructure that inherits authentication middleware but not the full authorization layer.

**Code patterns to flag:**
- Admin or organization-scope endpoint handler that calls auth middleware but does not check the caller's role/scope before executing
- HTTP method-based authorization gap: GET guarded but POST/PUT/DELETE not explicitly checked on the same path
- Internal or debug endpoint accessible without elevated credentials in a production deployment

**Mitigations available:**
- Every new extensibility-api or AI-platform handler calls an APS policy lookup function (`aps.check()` or equivalent) before returning data or executing an operation — absence of any APS check in the handler body is the failure signal
- Separate administrative endpoints from user-facing endpoints; require distinct scopes for admin operations
- ServiceNow CVE-2025-12420 (CVSS 9.3) is the canonical failure case: AI platform API endpoints that skip identity validation before establishing a session

**Source:** OWASP API Security Top 10 (2023)

---

## OWASP-API06: Unrestricted Access to Sensitive Business Flows

**Maps to threat category:** Blast Radius

**In the Tundra stack:** App installation, app action invocation, and webhook dispatch are the business flows that can be abused at scale. Bulk app installation across all spaces in an organization, automated mass invocation of AppActions, or scripted webhook triggering without rate limiting are the abuse patterns. This is operationally distinct from resource exhaustion — the calls are individually valid but the volume harms other tenants.

**Code patterns to flag:**
- App installation or app action endpoint with no per-org or per-user rate limit
- Webhook registration allowing unlimited webhook count per space/org without quota enforcement

**Mitigations available:**
- Business-logic rate limiting on sensitive operations (app install, bulk action invocation), calibrated to expected legitimate use
- Quota controls on webhook count per space and per org

**Source:** OWASP API Security Top 10 (2023)

## OWASP-API07: Server Side Request Forgery (SSRF)

**Maps to threat category:** Input Validation / Blast Radius

**In the Tundra stack:** Webhook URL registration is the primary SSRF surface in Tundra: a caller can register a webhook that points to `169.254.169.254` (AWS instance metadata), internal services, or Contentful-internal endpoints. The app framework's ability to define app URLs and callback endpoints is a secondary surface. SSRF in an AWS environment can yield IAM credentials from the metadata service.

**Code patterns to flag:**
- Webhook destination URL accepted and used without validation against an allowlist of permitted schemes and destination ranges
- User-supplied URL fetched server-side (link preview, webhook ping, URL import) without blocking RFC 1918 and cloud-metadata IP ranges
- URL allowlist bypass via redirect chains or URL parsing inconsistencies (`http://attacker.com@internal.host/`)

**Mitigations available:**
- Validate and sanitize all user-supplied URIs against a strict allowlist; disable unused schemes (file://, gopher://)
- Block access to cloud metadata endpoints (169.254.169.254, fd00:ec2::254) and RFC 1918 ranges at the network layer
- Enforce DNS rebinding protections

**Source:** OWASP API Security Top 10 (2023)

## OWASP-API08: Security Misconfiguration

**Maps to threat category:** Data Exposure / Blast Radius

**In the Tundra stack:** API-specific misconfiguration in Tundra includes: overly permissive CORS on the extensibility-api (the app proxy must enforce origin restrictions), verbose error responses from the app hosting execution layer, and unauthenticated `/health` or `/metrics` endpoints. In the Cloudflare Worker deployment, workers without wrangler-enforced environment variables default to predictable behavior.

**Code patterns to flag:**
- `Access-Control-Allow-Origin: *` on an authenticated extensibility-api or app-proxy route
- Error response returning `error.stack`, internal path strings, or SQL fragment to the caller
- `/metrics` or `/health` endpoint with no authentication in a Cloudflare Worker or Node service

**Mitigations available:**
- CORS policy allowlist: only the Contentful web app origin and explicitly authorized partner origins
- Error responses sanitized of stack traces, internal paths, and SQL fragments before reaching clients

**Source:** OWASP API Security Top 10 (2023)

## OWASP-API09: Improper Inventory Management

**Maps to threat category:** Dependency / Supply Chain

**In the Tundra stack:** The app framework exposes multiple API versions and internal endpoints across the extensibility-api, app proxy, and functions dispatch layer. Deprecated API versions (`/v1/` endpoints) that lack modern auth middleware and undocumented internal endpoints accessible without the API gateway's security layer are the Tundra-specific risk. Shadow APIs — microservice endpoints deployed without Security Team awareness — are the gap in new AI platform additions.

**Code patterns to flag:**
- Versioned API endpoint (`/v1/`, `/v2/`) where an older version lacks the auth/rate-limiting controls applied to the current version
- Internal microservice endpoint not covered by the API gateway's authentication layer
- API route not present in the OpenAPI/Swagger spec but accessible in production

**Mitigations available:**
- All routes present in `wrangler.toml` or the service's route manifest; OpenAPI/Swagger spec committed alongside code and diff-checked in CI
- Internal microservice APIs sit behind the API gateway's auth and rate-limiting middleware; bypass routes require explicit `internal_only: true` annotation

**Source:** OWASP API Security Top 10 (2023)

## OWASP-API10: Unsafe Consumption of APIs

**Maps to threat category:** Input Validation

**In the Tundra stack:** The app framework enables apps to integrate with arbitrary third-party APIs; data returned from those integrations can flow into Contentful content, webhook payloads, or AI agent contexts. A compromised or malicious third-party API response that returns unsanitized HTML, SQL-injectable values, or embedded LLM instructions is an indirect injection via API. This is Contentful's Secure Development Policy principle: "approach external services with caution and validate their behavior."

**Code patterns to flag:**
- Third-party API response rendered directly to HTML without sanitization (DOMPurify or equivalent)
- Third-party API response passed to a database query or shell command without validation
- Third-party API response incorporated into an AI agent's context without being labeled as untrusted content

**Mitigations available:**
- Apply identical validation and sanitization to third-party API data as to direct user input
- Treat external API responses as untrusted; apply context-appropriate encoding before rendering, storing, or passing to an LLM

**Source:** OWASP API Security Top 10 (2023)
