# Codex kickoff host

This is the Codex dispatch portion of the top-level kickoff skill. It replaces only how that skill's Direct Class calls invoke a Class and read its reply. Everything else in that skill applies unchanged: the routing, the sources, the Jira description addition, the brief fields, the change note, and the local plan review and approval. Set `<plugin root>` to the absolute folder that holds the top-level `skills/` and `runtime/` folders. Use `node <plugin root>/runtime/bin/cli.mjs` as the CLI (`<cli>` below). In every shared command, replace `${CLAUDE_PLUGIN_ROOT}` with that absolute path; never leave it for the shell to expand.

Your first message tells the person that tool and path enforcement on Codex is best effort. Before the first Class call, confirm native `spawn_agent` and `wait_agent` tools, an active `CODEX_SESSION_ID`, and a writable Kiln state folder. The session's sandbox must allow writes under `${XDG_STATE_HOME:-$HOME/.local/state}/kiln/`, where the Jira read requests and the Designer's receipt go; a refused write there, which the CLI reports with a system error code such as `EPERM` or `EACCES` in place of a `KILN_` code, means stop and say so. Every Class inherits the active session's model and reasoning effort; never name a model. Choose one scratch folder outside the plugin source (`<scratch>` below), and give each Class dispatch its own folder inside it, so that no dispatch overwrites the brief, report, or reply of another.

## Prospector and Planner

1. Run `node <cli> classes --host codex --class <id> --installed <body path>`. The body path is `<plugin root>/runtime/hosts/codex/agents/prospector.md` for `kiln:prospector` and `<plugin root>/runtime/hosts/codex/agents/planner.md` for `kiln:planner`. Stop on a stale installed body.
2. Make this dispatch's folder with `mkdir -p <scratch>/<name>-<n>`, where `<name>` is `prospector` or `planner` and `<n>` counts that Class's dispatches in this kickoff, from 1. Write the brief there as `brief.json`, as the shared skill says. For the Prospector, set `reportPath` to `<scratch>/prospector-<n>/prospector-report.md`, the file name the prospector skill uses, so a second Prospector call never overwrites a report whose hash a brief may already cite. Run `node <cli> class-check --host codex --class <id> --input <brief path>`. Stop and fix an invalid brief before dispatch.
3. Spawn exactly one native Codex subagent with `spawn_agent`, `fork_context: false`, and the `default` agent type. Omit a model override. The prompt names the brief path, the body path, and the brief's `reportPath` for the Prospector or its `planPath` for the Planner. Tell the member to read the body and then the brief before work. When the brief has numbered `checks`, list each one exactly as the brief writes it, as the numbered checks to run; a kickoff Planner brief has none. Ask for exactly one JSON outcome array and no prose outside it. Keep the returned agent ID.
4. Call `wait_agent` for that agent ID until it completes. Never substitute a different child or a summary from this thread. On an error or an interruption, report the limit and do not invent an outcome.
5. Run `node <plugin root>/runtime/hosts/codex/bin/reply.mjs --agent <agent ID> --marker <brief path> --out <scratch>/<name>-<n>`. It reads the subagent's own rollout and writes `reply.txt` (the one-item array), `reply.json` (its sole object), and `meta.json` (the model binding and the measured usage) beside the brief. Run `node <cli> class-check --host codex --class <id> --output <scratch>/<name>-<n>/reply.json` before you use the outcome.
6. If the script refuses with `CODEX_REPLY_INVALID`, or `class-check` refuses the reply, send one correction to the same subagent that names the defect, and call `wait_agent` again. The script never overwrites a reply, so make the correction's folder with `mkdir -p <scratch>/<name>-<n>-c` and run the script again with the same agent ID and `--out <scratch>/<name>-<n>-c`. Check `reply.json` there. If the reply still fails, or the script refuses with another code, report the limit. Do not ask the person to repair an internal receipt.

A Planner change note from the shared rules is a new dispatch, not a correction: write the changed brief into the Planner's next folder, `<scratch>/planner-<n>/` with `<n>` one higher, and after `class-check --input` passes on it, follow steps 3 to 6 again with a new subagent.

## Designer

Run `node <cli> classes --host codex --class kiln:designer --installed <plugin root>/runtime/hosts/codex/skills/shape/SKILL.md`, then make the Designer's folder with `mkdir -p <scratch>/designer-<n>`, with `<n>` counted as in step 2, write the brief there as `brief.json`, and run `class-check --host codex --class kiln:designer --input <brief path>`. Read `<plugin root>/runtime/hosts/codex/skills/shape/SKILL.md` and follow it in this thread with the argument `--brief <brief path> --cli <plugin root>/runtime/bin/cli.mjs`. It binds the Designer to the session's model and writes its receipt folder, with `output.txt` and `meta.json`. Copy the sole object of that `output.txt` unchanged into `<scratch>/designer-<n>/outcome.json`, and run `node <cli> class-check --host codex --class kiln:designer --output <that file>`.

## Usage

Report the measured usage from each `meta.json`: the last reply folder's for each Prospector or Planner dispatch (its `-c` folder after a correction), and the Designer's receipt folder's for the Designer. A reply folder's `meta.json` covers the whole subagent, its correction included, so never add an earlier folder to it. The Designer's `meta.json` already counts each subagent it started, under `usage.children`, so never add their usage to it again. When a `meta.json` is missing or has no `usage`, call that usage unmeasured, and do the same for each child that the Designer's `meta.json` names under `usage.unmeasuredChildren`.

## Jira

The plugin's hook file runs on Codex, so the guarded edit hook runs here, and with `KILN_JIRA_VIEW` unset, `jira-capability` reads the ticket through the capture path. The description addition itself (`jira-preview`, `jira-write-start`, and `jira-write-finish`) still needs `KILN_JIRA_VIEW`, as the shared Jira steps say. When a command refuses with `KILN_JIRA_READ_NEEDED`, call the session's tool whose name ends in `getJiraIssue` once for each key in `details.keys`, with `issueIdOrKey` and `cloudId` only, and run the command again. Before the first Jira read, tell the person in one line: on Codex the ticket text stays in this session after the read, because Codex cannot replace a tool's output, and a failed Jira edit may end as an attempt without a tool response, which needs manual resolution.
