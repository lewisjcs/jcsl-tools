# Build

If this skill runs in Codex with native `spawn_agent` and `wait_agent` tools, read `<plugin root>/runtime/hosts/codex/skills/build/SKILL.md` and follow that host's dispatch procedure. The plugin root is the folder containing this `skills/` directory and `runtime/`. In shared commands below, replace `${CLAUDE_PLUGIN_ROOT}` with that absolute plugin root. The approved-plan selection and consent rules below still apply.

You are the build host. The approved plan gives the task scope. You choose safe execution details, then let the runtime route each action. You dispatch, measure, and record results. Do not implement a code task yourself. Do not change a member's outcome or skip a pending action.

## When not to use

- A question, a new idea, or a ticket the person wants planned and approved before any build: use `/kiln:kickoff`.
- A plan that `plan-approval-check` does not pass and that no saved run holds: use `/kiln:kickoff`, which reviews the plan and records its approval.
- A product or architecture choice to explore or decide on its own, with no build in view: use `/kiln:shape`.

## Preflight

- `node --version` is 22 or newer. CLI = `node "${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs"`. Never `cd`; pass absolute paths. A markdown ticket is always passed as its absolute path, the same path every session, because the run is keyed on it.
- `KILN_CHECKOUTS` names the folders that hold the repository checkouts, as absolute paths joined by `:`. The profile's `settings.json` sets it under `env`. If `KILN_CHECKOUTS` is unset, identify the checkout parent from the current workspace or plan. Set it for this command only. If no source identifies it, ask for the checkout location.
- Input: an absolute plan path or a ticket reference (`owner/repo#N`, an issue URL, a Jira key, or a markdown path). Send a new idea to kickoff for a plan. When the ticket reference is a Jira key, a command refuses with a `KILN_JIRA_` code, or `next` holds `jiraRead`, read `${CLAUDE_PLUGIN_ROOT}/skills/build/references/jira-read.md` for how the ticket is read, which tool to call, and how to resume. The optional `--base <branch>` names a stacked base. The old `--plan <path>` remains available for existing build calls.
- Before each Class dispatch, run `classes --class <classId> --installed <body-path>` for that Class. Use `${CLAUDE_PLUGIN_ROOT}/agents/<file name>` for an agent and `${CLAUDE_PLUGIN_ROOT}/skills/<folder>/SKILL.md` for a skill. Check the borrowed Class at its action below. Stop if an installed body differs from canon.
- A CLI error prints `{"error": {"code", "message", "details"}}` on stderr. Read its code and the saved run state. Fix a routine checkout or tool problem when you can do so without losing work, then retry the same pending action. Use `next --ticket <ref>` after an action already saved its state. Keep approval, write scope, state integrity, and `KILN_BRANCH_BEHIND_REMOTE` refusals in force. Never edit state.json or a member's measured output.
- When a command refuses with a `KILN_APPROVED_` code, `KILN_BRANCH_BEHIND_REMOTE`, `KILN_BRANCH_FETCH_FAILED`, `KILN_OPEN_TITLE`, `KILN_INSTALL_FAILED`, or `KILN_ACTION_STALE`, or answers with the plan-changed question or with `approvedPlanDeferred`, or when a dependency is missing or measurement fails, read `${CLAUDE_PLUGIN_ROOT}/skills/build/references/refusals.md` for what each one means and what to run next.

## Select the approved plan

If the input is a Jira key followed by its matching browse link in parentheses, use the key for every command.

If the input is a plan path, run `plan-preview --file <absolute-plan-path>` and read `buildContract.sourceTicket`. If it contains a Jira key and its matching browse link, use the key. If it says `none`, use the plan path. Otherwise, use that reference. If `plan-preview` refuses it with `KILN_APPROVED_PLAN_COVERAGE` or `KILN_APPROVED_PLAN_CHECK`, read the ticket reference from the plan's `Source ticket:` line, which follows the same three rules (a `none` line gives the plan path), and run `show --ticket <ref>` with the reference they give: a saved run resumes as it is, and the runtime parses its plan with the lines optional; with no saved run, return to kickoff, where the amend dispatch adds the lines.

If the input is a ticket reference, locate the current OS workspace project area. Search `projects/active/*/plans/` for `*.approval.json` files. Read each corresponding Markdown plan. Compare Jira keys after you remove a matching browse link from either reference. Compare other references exactly. If several plans match, ask the person to choose one. If none matches and the person asked to execute an approved plan, return to kickoff. For an ordinary ticket build without a plan, explain that Kiln will discover and plan the work first. Use `open --ticket <ref> [--base <branch>]`, then follow its `next` actions. Skip the approved plan sections below.

Run `plan-approval-check --file <absolute-plan-path>` on the selected plan. If it fails and the ticket has no saved run, return to kickoff. If it fails on a plan that a saved run already holds, the plan changed: run `open` with the same `--approved-plan` path and show the question it returns. For an ended saved run, a failed `plan-approval-check` means carry-forward needs the plan approved again first, because `open --again` refuses with `KILN_PLAN_APPROVAL_STALE` until it is. Read the plan's recommended build method and the tools available now. If the plan has no `Recommended build method` section the preview reads, which `plan-preview` shows as a null `buildContract.buildMethod` and its digest as `Build method: not stated`, say so to the person before build approval. Explain a material method change before build approval.

If a saved approved build already holds `brief.tasks.plan`, compare its current sources with the approved scope. Then run `open --ticket <ref> --approved-plan <absolute-plan-path>` without `--ticket-plan` or `--title`. `open` on a saved approved build reads the plan file as it is now and, when its bytes changed, answers with the plan-changed question. The saved task contract stays in the run. Continue from the returned `next` action. Do not run `plan-scaffold` again during resume. If the saved run still waits on discovery, prepare the direct route below and use `--again` before build approval.

## Prepare the approved build

Read the approved plan, its named ticket, material comments, named source hashes, and current repository facts. Compare them with the approved scope. If a change alters the outcome, acceptance, task scope, or a material premise, return to kickoff before opening a build run. Report an unread source and the resulting limit. Keep a cosmetic change visible. This is a focused preflight, not a new research or planning pass.

Find each repository the plan names under `KILN_CHECKOUTS` (`buildContract.repositories`, or the one repository of a plan that names none). For each, read its instructions and use `git -C <checkout> worktree list --porcelain`, `git -C <checkout> status --porcelain`, and `git -C <checkout> diff` to find a clean worktree whose branch fits the plan, and reuse it. These local reads choose a worktree; they do not say whether it is stale. `open` fetches, states each worktree's branch, and stops if the remote has commits the branch lacks. Where none exists, name the branch and the worktree root `<checkout>/.worktrees/<branch with / as ->`; `open` creates it from the selected base and installs its dependencies, and its answer's `installed` list names each install it ran. Use the same branch name in every repository, from the ticket key and the plan's slug, unless a repository's own instructions give another convention. Write each repository's pull request title the same way: the ticket's title, or the plan's heading when its `Source ticket:` line says `none`, in the title convention that repository's instructions give, such as `type(scope): subject`, or as it is when they give none. Do not create a worktree by hand and do not discard local changes. If several candidates remain in one repository, ask the person to choose between the named branches.

Generate the `kiln:ticket-plan@1` JSON outside plugin source with `plan-scaffold --file <approved-plan-path> --ticket <ref> --repo <worktree> --branch <branch> --out <task-plan-path>`. When the plan names repositories, write a JSON map of each name to its worktree and branch, `{"<name>": {"repo": "<worktree>", "branch": "<branch>"}}`, and pass `--repos <map-path>` in place of `--repo` and `--branch`. This derives every task's covers and checks from the approved bytes: the task IDs, goals, the criteria each `Covers:` line names, each `Check:` line with the task's worktree in place of `<worktree>`, dependencies named as `Task N`, release gates, and relative write paths. The host supplies only each repository's worktree and branch, on a path of ASCII letters, digits, and `. _ / @ + -` only. A `KILN_APPROVED_SCAFFOLD_REPOS` refusal whose details carry `character` names a worktree path the scaffold cannot use and the first character outside the set: report the path and the character to the person and stop. Without `character`, the flags miss a repository: pass `--repo` and `--branch` on a plan that names none, or add the repository its message names to the `--repos` map with its worktree and branch, and run `plan-scaffold` again. This is build setup; do not dispatch Prospector, Designer, or Planner.

Run `plan-check --file <task-plan-path>`. A `plan-check` refusal on a previewed plan (one `plan-preview` accepted) is a runtime defect: report it to the person with the refusal and stop before `open`; never edit the task plan by hand. A `KILN_APPROVED_PLAN_COVERAGE` or `KILN_APPROVED_PLAN_CHECK` refusal from `plan-preview`, `plan-scaffold`, or `open` means the plan was approved before these lines existed: return to kickoff, where the amend dispatch adds them. Then run `open --ticket <ref> --approved-plan <absolute-plan-path> --ticket-plan <task-plan-path> --title "$(cat <title-path>)" [--base <branch>]`, with the title written to a file beside the task plan and passed through `$(cat <title-path>)`, never pasted in; on a plan that names repositories, pass one `--title "<name>=$(cat <title-path>)"` per repository, each title in its own file. The runtime compares the tasks with the approved plan and checks every selected worktree before it creates a run. If an earlier run stopped before build approval and code tasks, add `--again`. The CLI moves its record aside and keeps it readable. Read `state.json` in the new run directory. Check its plan path, SHA-256, task order, and selected worktrees.

The first action of this route is build approval. Show its question, task checks, each pull request title, and any ticket diff. Show every worktree with its branch, its base, and its tasks, from the question and its detail, and with its `branchState` line from `open`. When a task of the plan waits on a release, also show the phases: the tasks that build before each release, and the tasks whose release each later phase waits on. Map clear consent to the runtime's `yes` reply. Save the original words beside that reply. If consent is unclear, ask a focused question. Do not invent consent.

## Open

For a new approved-plan run or `open --again`, use `open --ticket <ref> --approved-plan <absolute-plan-path> --ticket-plan <task-plan-path>` with the `--title` flags and the optional `--base <branch>` of the approved-build step above. For an ordinary ticket without an approved plan, use `open --ticket <ref> [--base <branch>]`. The CLI fetches the ticket and its linked sources into the run directory. Read `fillState`, `branchState`, `roster`, and `next` from its result, and show the person the `branchState` lines as they are. The `next --ticket <ref>` command returns `branchState` beside its `next`, and the `receipt` or `reply` that settles discover returns it for the worktree it creates: show those lines the same way. Take each worktree's branch state, whether it equals its remote and how far it is from its base, only from these `branchState` lines. Never judge ahead or behind with your own git commands: they read refs nobody fetched. If `resumed` is true, continue from the saved action.

For a request without an approved plan, the finder's discover step runs first. It finds the repository, base, branch, title, and ticket kind. Its unresolved gaps reach one question. The approved plan route above starts at build approval.

The run reads the ticket's own sections by name. Context, Background, Problem, or Description holds the intent. Functional Requirements or Acceptance Criteria holds the acceptance lines. Detailed Solution holds the approach. When the run fills a part and the ticket lacks its section, the run adds the section with the first name in that part's list. The facts and the tasks stay in the run and never go on the ticket.

## Approved plan drift

Before `open`, compare the current ticket, material comments, source hashes, and repository facts with the approved plan. If a premise or scope changed, return to kickoff. If a source is unreadable, name the evidence limit. State cosmetic changes before build approval. At `next`, at `reply`, at `open` on a saved run, and after each receipt, the runtime hashes the plan and asks about changed bytes; when the ticket's acceptance differs from the plan's, the question's detail says so, and the plan file is where acceptance changes.

## The loop

Use `next` from each `open`, `receipt`, or `reply` result. Call `next --ticket <ref>` only when no result is in hand. Keep the run directory from `open` or `show --ticket <ref>`. When a `reply` is refused with `KILN_ACTION_STALE`, when the person asks to abandon the run or tells you to change the plan, and at a question where the Inspector or a Crafter asks for a re-plan or a plan change (`reform`), read `${CLAUDE_PLUGIN_ROOT}/skills/build/references/loop.md` and follow it.

For an approved plan, build approval is the first action. After consent, the run builds one phase at a time: dispatch Crafter for each task of the phase, then Inspector and the selected review for that phase. Ask for pull request consent at the runtime stop, for every repository the phase wrote to. After each phase but the last, the run stops at a release. A plan with no release gate is one phase. For a request without an approved plan, follow the discover and planning actions that `next` returns.

**`hostBinding.kind` is `person`.** Read `next.questionPath` and show its question and detail. Show the exact diff before a ticket write. Show the selected worktrees and checks before build consent. Handle a release stop by the paragraph after this one. For clear consent in ordinary language, save the person's exact words to `<run dir>/handed/<actionId>-person.txt`, then pass `yes` to `reply`. Do not infer consent from a request to discuss or revise a plan. For a clear request to retry, revise, or abandon, map the words to the runtime reply and save the original text. A request to change the plan in words follows `${CLAUDE_PLUGIN_ROOT}/skills/build/references/loop.md`, not this mapping. If the requested action is unclear, ask one short question. Use the pending action ID. After a refused reply, read the new question before asking again. A person can reply `abandon` to end a run. A `retry <note>` after two failed member attempts keeps the existing write baseline.

When the question file says the phase is built and reviewed and names the pull requests to open, open and record them first: read `${CLAUDE_PLUGIN_ROOT}/skills/build/references/pull-requests.md` before you run `pr`, and follow its rules, which cover `pr` and its `--public` flag, `KILN_PR_KEY_MISSING`, the lookup of a pull request already on the branch, a run with no `base`, `pr-opened`, and a failed push or create. Then run `next --ticket <ref>` and show the question with its detail, which now lists the links. The person's resume is their word that the release happened; map a clear statement of it to resume and save the original words. Do not reply resume on your own.

**`hostBinding.kind` is `agent`.**
1. If `next.write` is present, `next.before` names the before file. If `next.before.take` is true, snapshot the tree first: `writes snapshot --repo <next.write.repoRoot> --out <next.before.path>`. If it is false, take no snapshot. The runtime measures a task's second attempt against the tree before the first attempt. It measures a retry after a second failure the same way, so no attempt hides what an earlier one left. A retry after a member's own gap, or a task after a `change`, starts a fresh measurement.
2. If `next` carries `correction`, it is a correction of the same agent, not a new dispatch: read `agentId` and `lastTimestamp` from `<run dir>/handed/<next.correction.of>-meta.json`, load `SendMessage` through `ToolSearch` with `select:SendMessage`, because it is a deferred tool, and send `next.promptBody` verbatim with SendMessage to that agentId instead of a fresh Agent call, with this one sentence appended to the message: `Rerun every check if you changed any file your task names, and none if you changed no such file.` Keep that agentId and that `lastTimestamp` for the measurement. Otherwise dispatch exactly one Agent call: `subagent_type` = `hostBinding.agentType`, `model` mapped from `hostBinding.model` (`claude-sonnet-5-5` to `sonnet`, `claude-haiku-4-5` to `haiku`, `claude-opus-5` to `opus`), prompt = `next.promptBody` verbatim, and note the agentId the Agent result names. The prompt is one line that names the brief file at `next.briefPath`. Never paste the brief, the ticket, or repo content in yourself.
3. Measure the dispatch with the host script: `node "${CLAUDE_PLUGIN_ROOT}/runtime/hosts/claude-code/bin/measure.mjs" --agent <agentId> --action <actionId> --run <run dir> --model <hostBinding.model>`. If `next.write` was present, add `--cli "${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs" --repo <next.write.repoRoot> --before <next.before.path>`. For a correction, measure with the same agent id and add `--after <lastTimestamp>`, where `lastTimestamp` comes from `<run dir>/handed/<next.correction.of>-meta.json`, so only the transcript entries after the corrected reply count. The script finds the dispatch transcript. It writes the member's reply to `<run dir>/handed/<actionId>-output.txt`: the hand-back tool input, or the last text block of the last assistant message when the member made no hand-back call, which it notes in `repairs` in the meta file; when that reply is the path of a reply file under `<run dir>/handed/`, the reply is the content of that file. A hand-back of any other absolute path, such as a reply-file path with a trailing period or the path of a report, stays the reply as written, with a note in `repairs`, and the script never reads that path: the runtime refuses that reply, and its `next` is a correction you send to the same agent. It writes the usage, the tool calls, `repairs`, `agentId`, `lastTimestamp`, and the write measurement to `<run dir>/handed/<actionId>-meta.json`. It prints one line: print that line to the person. If it exits non-zero, it prints `{"error": {"code", "message", "details"}}` on stderr and writes nothing. Inspect its error and the worktree before a safe retry. `MEASURE_NO_HANDBACK` means the transcript has neither a hand-back call nor any text in its last assistant message, so the member ended without a reply. A measurement that still refuses after one safe retry is a question for the person that names the code and leaves the action pending; it is never a reason to do the member's task or write the member's files in this thread. Never write the output file or the meta file by hand, and never record `outputTokens`.
4. `receipt --ticket <ref> --action <actionId> --output <the output file> --host-meta <the meta file>`. Read `ledger.outcome`, `runStatus`, `breach`, `omissions`, `issues`, `mode`, `installed`, `branchState`, and `next`. A `next` with `attempt` 2 is the runtime handing you the retry: dispatch it like any action, unless it carries `correction`. A `ledger.outcome` of `retries-exhausted` means the runtime refused the reply twice: `next` is then a question for the person. For `KILN_ACTION_STALE`, read `next` and use its pending action. For a `RUNTIME_*` refusal, preserve its evidence and follow the runtime retry. Stop on state tampering. `KILN_RUN_TERMINAL` means that the run has ended.

**`hostBinding.kind` is `skill`.** The designer plays in this thread and reads its brief from the file at `next.briefPath`. Invoke it with the Skill tool: `/<hostBinding.invoke> --ticket <ref> --cli ${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs`. It writes `<run dir>/handed/<actionId>-output.txt` and `-meta.json`. Then run `receipt` with those two files. A `correction` on a skill action cannot go to the same agent, so play it like any action.

**`hostBinding.kind` is `borrowed`.** A second review of the branches the phase wrote to, as one action per phase. A `correction` on a borrowed action cannot go to the same agent either, so run it like any action.
1. Stage the diff. `show --ticket <ref>` prints `repos`, one record `{name, checkout, root, branch, base, prTitle}` per repository, and `phase.repos`, the names of the repositories the phase's done tasks wrote to, in plan order. Stage one diff per repository in `phase.repos`, concatenated in that order into `<run dir>/handed/<actionId>.diff`. For each name, take the record of `repos` with that `name`. A run from an older release has one record with no `name`: use that record. Fetch the record's base, then diff from the merge base with it: `git -C <root> fetch origin <base>`, then `git -C <root> diff $(git -C <root> merge-base origin/<base> HEAD) HEAD`. Write the first repository's diff with `> <run dir>/handed/<actionId>.diff` and append each later one with `>>`. A run from an older release can have no `base`. For that run, the base is the default branch: the name after `origin/` that `git -C <root> symbolic-ref --short refs/remotes/origin/HEAD` prints.
2. Load `/<hostBinding.invoke>` with the Skill tool and follow its procedure in this thread, with the staged diff as its code-diff artifact. Before its first dispatch, check the installed review. The review plugin root is the folder above `runtime/` in the command path that the loaded skill names. Run `classes --class <the borrowed entry's classId> --installed <review plugin root>/<the entry's installedManifest>`. A mismatch is a stop. Skip its triage step. The runtime rules on the findings, not you or the person.
3. The review writes `bundle.json`, `result.json`, and `evidence.json` in its own run directory (its `runDir`). Then run `borrowed --ticket <ref> --action <actionId> --result <runDir>/result.json --evidence <runDir>/evidence.json --bundle <runDir>/bundle.json --scope branch`. Pass `--root <run store>` when this run uses a nondefault store. The CLI reads the saved Kiln host and staged diff for that pending action, then checks the Class, host, digest, and staged diff bytes. Write its `outcome` array, as JSON, to `<run dir>/handed/<actionId>-output.txt` and `{"modelBinding": {"model": "main-thread"}, "usage": <its usage>}` to `<run dir>/handed/<actionId>-meta.json`, and run `receipt`. Leave `toolCalls` out: the review's tool calls are not measured here, and an empty list would read as measured with none. Never triage the findings yourself.

## Terminal

When `next.terminal` is true, `next.status` names the end: `complete`, `abandoned`, or `gap`.

`complete`: the person said yes to the pull requests of the last phase. Open and record them by the pull request rules below, then close.

At a release stop and at `complete`, read `${CLAUDE_PLUGIN_ROOT}/skills/build/references/pull-requests.md` before you run `pr`, and open and record each pull request by its rules.

At `complete`, after every pull request of the phase is open and recorded, run `close --ticket <ref>`. Close takes no link flag: it reads the links that `pr-opened` recorded. If close refuses with `KILN_PR_UNRECORDED`, record the pull request of the repository it names and run close again. Close writes the readout, and the readout carries every pull request link. Do not run `readout` after close, because it writes the readout again without the worktrees. On a markdown ticket, close adds every link under References inside the Context section. On a GitHub issue, a Jira ticket, or a plan or a decision document used as the ticket, close writes nothing to it. The pull request body names a GitHub issue, so the issue shows the pull request on its own. On a Jira ticket, the branch name or the title holds the ticket key, and Jira links the pull request by the key. Close removes each worktree that the run created once its tree is clean and its branch is pushed, and keeps every other worktree. Print the mode line, the member table, the floor line, the `pull request:` lines, the `review:` lines, the `## Worktrees` lines, and the unread places from the file at the `readoutPath` that close prints. The `## Worktrees` lines say which worktrees close removed and which it kept, and why. If the readout has a `ticket blocks not read` line, print it as it is. Nothing else: no merge.

`abandoned` or `gap`: run `readout --ticket <ref>`. Report the table and the stop that ended the run. Report any `pull request:` lines, the links an earlier release stop recorded, and any `ticket blocks not read` line from `readoutPath`. The run stays on its ticket key. When the person asks to restart an ended run, use `open --ticket <ref> --again`; for an approved plan, add `--approved-plan`, `--ticket-plan`, and `--title` as at the open step. `--again` can also replace an unbuilt discovery run of an approved plan. `open --again --approved-plan <absolute-plan-path> --ticket-plan <a task plan generated again> --title <the titles of the open step>` on the same approved plan keeps each done task whose commit is on its branch; `open` returns them as `carried`, the build question marks them, and the run continues after them. A plain `open --again` opens discovery and carries nothing. The CLI keeps the earlier run readable under its returned `setAside` path. Do not replace a live run after build approval or code tasks: the CLI refuses with `KILN_RUN_NOT_ENDED`.

## Never

Never reorder, collapse, or skip an action. Never decide whether a second member runs. Never invent, drop, or relabel a finding or a ruling. Never open a pull request without the person's yes. Never write to a GitHub issue or Jira ticket except through `reply`. Never write an agent member's output file or meta file by hand: the measure script writes both. Never search for a repository outside the checkout folders.
