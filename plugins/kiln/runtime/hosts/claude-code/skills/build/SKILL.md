# Build

If this skill runs in Codex with native `spawn_agent` and `wait_agent` tools, read `<plugin root>/runtime/hosts/codex/skills/build/SKILL.md` and follow that host's dispatch procedure. The plugin root is the folder containing this `skills/` directory and `runtime/`. In shared commands below, replace `${CLAUDE_PLUGIN_ROOT}` with that absolute plugin root. The approved-plan selection and consent rules below still apply.

You are the build host. The approved plan gives the task scope. You choose safe execution details, then let the runtime route each action. You dispatch, measure, and record results. Do not implement a code task yourself. Do not change a member's outcome or skip a pending action.

## Preflight

- `node --version` is 22 or newer. CLI = `node "${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs"`. Never `cd`; pass absolute paths. A markdown ticket is always passed as its absolute path, the same path every session, because the run is keyed on it.
- `KILN_CHECKOUTS` names the folders that hold the repository checkouts, as absolute paths joined by `:`. The profile's `settings.json` sets it under `env`. If `KILN_CHECKOUTS` is unset, identify the checkout parent from the current workspace or plan. Set it for this command only. If no source identifies it, ask for the checkout location.
- Input: an absolute plan path or a ticket reference (`owner/repo#N`, an issue URL, a Jira key, or a markdown path). Send a new idea to kickoff for a plan. A Jira key is read in one of two ways, and this release never writes to Jira. If the setting `KILN_JIRA_VIEW` names a command, the runtime runs that command to read the ticket. The setting can also name a script of the person's own that prints one ticket as JSON. With no setting, the runtime reads the ticket through this session's Jira read tool, and it tells you when to call the tool: the refusal `KILN_JIRA_READ_NEEDED` lists ticket keys in `details.keys`. If the session lists that tool by name only, load it first. For each key, call the tool whose name ends in `getJiraIssue` once, with `issueIdOrKey` set to the key and `cloudId` set to the Jira site, and with no other input. A hook sets the other inputs and saves the answer for the runtime. The tool's result is then one line with no ticket text. That is correct: never call the tool again to see the ticket, and never write a ticket file yourself. To find the cloud id, call the tool of the same Jira server that lists the sites you can reach. If it lists more than one site, ask the person which site holds the ticket. If the call fails for one key, go on to the next key. After a `KILN_JIRA_READ_NEEDED` at `open`, run `open` again with the same flags. `open` can ask twice: once for the ticket and once for the tickets that it links to. After a `KILN_JIRA_READ_NEEDED` at a later command, run `next --ticket <ref>`. A command that already saved its state does not refuse for a read, and a command that only shows the run does not refuse either. The `next` of its answer then holds `jiraRead` in place of an action. Read the other fields of that answer as always. Then call the tool once for each key in `next.jiraRead.keys`, and run `next --ticket <ref>`. If the session has no tool whose name ends in `getJiraIssue`, show the refusal's message to the person and stop. For another `KILN_JIRA_` refusal, read the named capture and correct a safe tool or command setup error. Preserve an unreadable capture and report the limit. `KILN_JIRA_NOT_READ` means that no answer was saved: the session has no Jira read tool, the call failed, or the session started before the plugin update. `KILN_JIRA_CAPTURE` means that the saved answer cannot be used, and its message names the kept file. Never run a login for the person. After such a refusal on a later command, resume with `next --ticket <ref>`, not with the command that failed. If `next` names the action whose command failed, run that command again: a `receipt` with its files in `<run dir>/handed/`, a `reply` with the same text from the person. The optional `--base <branch>` names a stacked base. The old `--plan <path>` remains available for existing build calls.
- Before each Class dispatch, run `classes --class <classId> --installed <body-path>` for that Class. Use `${CLAUDE_PLUGIN_ROOT}/agents/<file name>` for an agent and `${CLAUDE_PLUGIN_ROOT}/skills/<folder>/SKILL.md` for a skill. Check the borrowed Class at its action below. Stop if an installed body differs from canon.
- A CLI error prints `{"error": {"code", "message", "details"}}` on stderr. Read its code and the saved run state. Fix a routine checkout or tool problem when you can do so without losing work, then retry the same pending action. Use `next --ticket <ref>` after an action already saved its state. Keep approval, write scope, and state integrity refusals in force. Never edit state.json or a member's measured output.

## Select the approved plan

If the input is a Jira key followed by its matching browse link in parentheses, use the key for every command.

If the input is a plan path, run `plan-preview --file <absolute-plan-path>` and read `buildContract.sourceTicket`. If it contains a Jira key and its matching browse link, use the key. If it says `none`, use the plan path. Otherwise, use that reference.

If the input is a ticket reference, locate the current OS workspace project area. Search `projects/active/*/plans/` for `*.approval.json` files. Read each corresponding Markdown plan. Compare Jira keys after you remove a matching browse link from either reference. Compare other references exactly. If several plans match, ask the person to choose one. If none matches and the person asked to execute an approved plan, return to kickoff. For an ordinary ticket build without a plan, explain that Kiln will discover and plan the work first. Use `open --ticket <ref> [--base <branch>]`, then follow its `next` actions. Skip the approved plan sections below.

Run `plan-approval-check --file <absolute-plan-path>` on the selected plan. If it fails and the ticket has no saved run, return to kickoff. If it fails on a plan that a saved run already holds, the plan changed: run `open` with the same `--approved-plan` path and show the question it returns. For an ended saved run, a failed `plan-approval-check` means carry-forward needs the plan approved again first, because `open --again` refuses with `KILN_PLAN_APPROVAL_STALE` until it is. Read the plan's recommended build method and the tools available now. Explain a material method change before build approval.

If a saved approved build already holds `brief.tasks.plan`, compare its current sources with the approved scope. Then run `open --ticket <ref> --approved-plan <absolute-plan-path>` without `--ticket-plan`. `open` on a saved approved build reads the plan file as it is now and, when its bytes changed, answers with the plan-changed question. The saved task contract stays in the run. Continue from the returned `next` action. Do not translate the plan again during resume. If the saved run still waits on discovery, prepare the direct route below and use `--again` before build approval.

## Prepare the approved build

Read the approved plan, its named ticket, material comments, named source hashes, and current repository facts. Compare them with the approved scope. If a change alters the outcome, acceptance, task scope, or a material premise, return to kickoff before opening a build run. Report an unread source and the resulting limit. Keep a cosmetic change visible. This is a focused preflight, not a new research or planning pass.

Find each repository the plan names under `KILN_CHECKOUTS` (`buildContract.repositories`, or the one repository of a plan that names none). For each, read its instructions and use `git -C <checkout> worktree list --porcelain`, `git -C <checkout> status --porcelain`, and `git -C <checkout> diff` to find a clean worktree whose branch fits the plan, and reuse it. Where none exists, name the branch and the worktree root `<checkout>/.worktrees/<branch with / as ->`; `open` creates it from the selected base and installs its dependencies, and its answer's `installed` list names each install it ran. Use the same branch name in every repository, from the ticket key and the plan's slug, unless a repository's own instructions give another convention. Do not create a worktree by hand and do not discard local changes. If several candidates remain in one repository, ask the person to choose between the named branches.

Generate the `kiln:ticket-plan@1` JSON outside plugin source with `plan-scaffold --file <approved-plan-path> --ticket <ref> --repo <worktree> --branch <branch> --out <task-plan-path>`. When the plan names repositories, write a JSON map of each name to its worktree and branch, `{"<name>": {"repo": "<worktree>", "branch": "<branch>"}}`, and pass `--repos <map-path>` in place of `--repo` and `--branch`. This copies the approved task IDs, goals, acceptance words, dependencies named as `Task N`, release gates, and relative write paths from the unchanged approved bytes, and gives each task the worktree and branch of its repository. A one-task plan covers every criterion automatically. For several tasks, write a small JSON map of task IDs to numbered criteria, such as `{"task-1":[1],"task-2":[2]}`, and pass it with `--coverage <map-path>`. Use the scaffold's `acceptanceChoices` and `spans` to check the mapping against the plan. Choose `doneWhen` commands from the repository's actual test tools. Write them as a JSON map of task IDs to arrays of `{command,expect,repo}` and pass `--checks <map-path>`. Each check names its own task's worktree, as its `repo` and in its command, and gives an observable expected result. Use an absolute form such as `npm --prefix <worktree> test` or `git -C <worktree> diff --check`. Confirm the scaffold reports `missing: []`. Add any other absolute input paths needed for execution without expanding the approved goal or file scope. This is build setup; do not dispatch Prospector, Designer, or Planner.

Run `plan-check --file <task-plan-path>`. Correct a coverage map or check shape error, then regenerate the scaffold. If the approved plan cannot support a task mapping, return to kickoff. Then run `open --ticket <ref> --approved-plan <absolute-plan-path> --ticket-plan <task-plan-path> [--base <branch>]`. The runtime compares the tasks with the approved plan and checks every selected worktree before it creates a run. If an earlier run stopped before build approval and code tasks, add `--again`. The CLI moves its record aside and keeps it readable. Read `state.json` in the new run directory. Check its plan path, SHA-256, task order, and selected worktrees.

The first action of this route is build approval. Show its question, task checks, and any ticket diff. Show every worktree with its branch, its base, and its tasks, from the question and its detail. When a task of the plan waits on a release, also show the phases: the tasks that build before each release, and the tasks whose release each later phase waits on. Map clear consent to the runtime's `yes` reply. Save the original words beside that reply. If consent is unclear, ask a focused question. Do not invent consent.

If `KILN_APPROVED_TASK_CHANGED` reports a JSON mapping error, correct the mapping and retry `open`. Return a real scope change to kickoff. When the plan file changed since approval, the next command answers with a question instead of an action: show its question and the diff in its detail. Pass the person's yes to continue on the new plan, `change <note>` for a Planner re-plan when the question offers it, or abandon. A question with no yes names what in the file must change first, such as a done task's identity or a file the runtime cannot read: fix the file and run `next`. While a member dispatch is pending, the runtime reads no plan file until that dispatch's receipt: an `open --approved-plan <path>` for another file returns that dispatch with `approvedPlanDeferred: <path>`, and you run it again after the receipt. `KILN_APPROVED_TASK_PLAN_REQUIRED` means that `open` got an approved plan with no task plan and no saved run: generate the task plan as above and pass `--ticket-plan`. `KILN_APPROVED_SOURCE` and `KILN_APPROVED_TICKET` mean that the task plan lacks the approved plan's source or the ticket: generate it again with `plan-scaffold`. `KILN_APPROVED_RUN_NEEDS_RESTART` means that the saved run still waits on discovery or planning: add `--again`. On a run that holds an approved plan, another `--approved-plan` file is a plan change and asks that question; on a run with no approved plan it is still `KILN_APPROVED_PLAN_RUN_MISMATCH`. If `KILN_APPROVED_BASE` says that a checkout names no origin default branch, run `git -C <checkout> remote set-head origin --auto` for the checkout its details name. Retry `open`. If the selected base is absent on that checkout's remote, choose a valid base within the plan and show it. `KILN_APPROVED_REPOSITORY` means that a worktree's checkout is not a repository directly under `KILN_CHECKOUTS`, that two worktrees share one checkout, or that a task's worktree belongs to another repository than the one its approved task names: correct that worktree and generate the task plan again. `KILN_APPROVED_WORKTREE` means that a root is neither the top of a registered worktree nor a missing root under `<checkout>/.worktrees/`: name a valid root. `KILN_APPROVED_WORKTREE_BRANCH` refuses the default branch, and a branch to create that already exists, locally or on the remote: name the worktree that holds that branch, or ask the person for another branch name. If `KILN_APPROVED_WORKTREE_DIRTY` appears, preserve the changes. Find a clean checkout or resume the run that owns them. If `KILN_INSTALL_FAILED` appears or a dependency is missing, run the repository's install command in the worktree. Resume with `next`. If `KILN_ACTION_STALE` appears, read `next` before acting. If measurement fails, inspect the worktree for writes and commits before a retry. Keep approval, state integrity, and measured write refusals in force.

## Open

For an approved plan, use `open --ticket <ref> --approved-plan <absolute-plan-path> --ticket-plan <task-plan-path> [--base <branch>]`. For an ordinary ticket without one, use `open --ticket <ref> [--base <branch>]`. The CLI fetches the ticket and its linked sources into the run directory. Read `fillState`, `roster`, and `next` from its result. If `resumed` is true, continue from the saved action.

For a request without an approved plan, the finder's discover step runs first. It finds the repository, base, branch, title, and ticket kind. Its unresolved gaps reach one question. The approved plan route above starts at build approval.

The run reads the ticket's own sections by name. Context, Background, Problem, or Description holds the intent. Functional Requirements or Acceptance Criteria holds the acceptance lines. Detailed Solution holds the approach. When the run fills a part and the ticket lacks its section, the run adds the section with the first name in that part's list. The facts and the tasks stay in the run and never go on the ticket.

## Approved plan drift

Before `open`, compare the current ticket, material comments, source hashes, and repository facts with the approved plan. If a premise or scope changed, return to kickoff. If a source is unreadable, name the evidence limit. State cosmetic changes before build approval. At `next`, at `reply`, at `open` on a saved run, and after each receipt, the runtime hashes the plan and asks about changed bytes; when the ticket's acceptance differs from the plan's, the question's detail says so, and the plan file is where acceptance changes.

## The loop

Use `next` from each `open`, `receipt`, or `reply` result. Call `next --ticket <ref>` only when no result is in hand. Keep the run directory from `open` or `show --ticket <ref>`. If a `reply` is refused with `KILN_ACTION_STALE` because the command's own plan check just replaced the question with a plan-changed question, read `next` and show the new question. A person can reply `abandon` at any pending action, a member dispatch included: run `reply` with the pending action id and the text `abandon`. At a dispatch, stop the running member before replying `abandon`; commits the member makes after the run ends are not tracked by carry-forward. When the person tells you to change the plan in words, such as `fix the plan: 0.35 to 0.25 in criterion 2 and task 3`, make that change in the plan file yourself, show the diff, and say that you edited on instruction. Then run `next`, or, while a member dispatch is pending, wait for its receipt instead. The runtime asks its plan-changed question over your edit, after the receipt when a member dispatch is pending, and the person's `yes` there rebinds the run. The same holds at the Inspector's re-plan question (`reform`): on the person's instruction fix the plan by hand, run `next`, and pass their `yes` to the plan-changed question it returns; or pass `change <note>` at the reform question when they want a Planner re-plan. A change that needs a look at the code is the Planner's: pass `change <note>` with the person's words.

For an approved plan, build approval is the first action. After consent, the run builds one phase at a time: dispatch Crafter for each task of the phase, then Inspector and the selected review for that phase. Ask for pull request consent at the runtime stop, for every repository the phase wrote to. After each phase but the last, the run stops at a release. A plan with no release gate is one phase. For a request without an approved plan, follow the discover and planning actions that `next` returns.

**`hostBinding.kind` is `person`.** Read `next.questionPath` and show its question and detail. Show the exact diff before a ticket write. Show the selected worktrees and checks before build consent. Handle a release stop by the paragraph after this one. For clear consent in ordinary language, save the person's exact words to `<run dir>/handed/<actionId>-person.txt`, then pass `yes` to `reply`. Do not infer consent from a request to discuss or revise a plan. For a clear request to retry, revise, or abandon, map the words to the runtime reply and save the original text. A request to change the plan in words follows the loop paragraph above, not this mapping. If the requested action is unclear, ask one short question. Use the pending action ID. After a refused reply, read the new question before asking again. A person can reply `abandon` to end a run. A `retry <note>` after two failed member attempts keeps the existing write baseline.

When the question file says the phase is built and reviewed and names the pull requests to open, open and record them first by the pull request rules under Terminal, which cover `pr` and its `--public` flag, `KILN_PR_KEY_MISSING`, the lookup of a pull request already on the branch, a run with no `base`, `pr-opened`, and a failed push or create. Then run `next --ticket <ref>` and show the question with its detail, which now lists the links. The person's resume is their word that the release happened; map a clear statement of it to resume and save the original words. Do not reply resume on your own.

**`hostBinding.kind` is `agent`.**
1. If `next.write` is present, `next.before` names the before file. If `next.before.take` is true, snapshot the tree first: `writes snapshot --repo <next.write.repoRoot> --out <next.before.path>`. If it is false, take no snapshot. The runtime measures a task's second attempt against the tree before the first attempt. It measures a retry after a second failure the same way, so no attempt hides what an earlier one left. A retry after a member's own gap, or a task after a `change`, starts a fresh measurement.
2. If `next` carries `correction`, it is a correction of the same agent, not a new dispatch: read `agentId` and `lastTimestamp` from `<run dir>/handed/<next.correction.of>-meta.json`, load `SendMessage` through `ToolSearch` with `select:SendMessage`, because it is a deferred tool, and send `next.promptBody` verbatim with SendMessage to that agentId instead of a fresh Agent call, with this one sentence appended to the message: `Rerun every check if you changed any file, and none if you changed no file.` Keep that agentId and that `lastTimestamp` for the measurement. Otherwise dispatch exactly one Agent call: `subagent_type` = `hostBinding.agentType`, `model` mapped from `hostBinding.model` (`claude-sonnet-5` to `sonnet`, `claude-haiku-4-5` to `haiku`, `claude-opus-5` to `opus`), prompt = `next.promptBody` verbatim, and note the agentId the Agent result names. The prompt is one line that names the brief file at `next.briefPath`. Never paste the brief, the ticket, or repo content in yourself.
3. Measure the dispatch with the host script: `node "${CLAUDE_PLUGIN_ROOT}/runtime/hosts/claude-code/bin/measure.mjs" --agent <agentId> --action <actionId> --run <run dir> --model <hostBinding.model>`. If `next.write` was present, add `--cli "${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs" --repo <next.write.repoRoot> --before <next.before.path>`. For a correction, measure with the same agent id and add `--after <lastTimestamp>`, where `lastTimestamp` comes from `<run dir>/handed/<next.correction.of>-meta.json`, so only the transcript entries after the corrected reply count. The script finds the dispatch transcript. It writes the member's reply to `<run dir>/handed/<actionId>-output.txt`: the hand-back tool input, or the last text block of the last assistant message when the member made no hand-back call, which it notes in `repairs` in the meta file. It writes the usage, the tool calls, `repairs`, `agentId`, `lastTimestamp`, and the write measurement to `<run dir>/handed/<actionId>-meta.json`. It prints one line: print that line to the person. If it exits non-zero, it prints `{"error": {"code", "message", "details"}}` on stderr and writes nothing. Inspect its error and the worktree before a safe retry. `MEASURE_NO_HANDBACK` means the transcript has neither a hand-back call nor any text in its last assistant message, so the member ended without a reply. A measurement that still refuses after one safe retry is a question for the person that names the code and leaves the action pending; it is never a reason to do the member's task or write the member's files in this thread. Never write the output file or the meta file by hand, and never record `outputTokens`.
4. `receipt --ticket <ref> --action <actionId> --output <the output file> --host-meta <the meta file>`. Read `ledger.outcome`, `runStatus`, `breach`, `omissions`, `issues`, `mode`, `installed`, and `next`. A `next` with `attempt` 2 is the runtime handing you the retry: dispatch it like any action, unless it carries `correction`. A `ledger.outcome` of `retries-exhausted` means the runtime refused the reply twice: `next` is then a question for the person. For `KILN_ACTION_STALE`, read `next` and use its pending action. For a `RUNTIME_*` refusal, preserve its evidence and follow the runtime retry. Stop on state tampering. `KILN_RUN_TERMINAL` means that the run has ended.

**`hostBinding.kind` is `skill`.** The designer plays in this thread and reads its brief from the file at `next.briefPath`. Invoke it with the Skill tool: `/<hostBinding.invoke> --ticket <ref> --cli ${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs`. It writes `<run dir>/handed/<actionId>-output.txt` and `-meta.json`. Then run `receipt` with those two files. A `correction` on a skill action cannot go to the same agent, so play it like any action.

**`hostBinding.kind` is `borrowed`.** A second review of the branches the phase wrote to, as one action per phase. A `correction` on a borrowed action cannot go to the same agent either, so run it like any action.
1. Stage the diff. `show --ticket <ref>` prints `repos`, one record `{name, checkout, root, branch, base, prTitle}` per repository, and `phase.repos`, the names of the repositories the phase's done tasks wrote to, in plan order. Stage one diff per repository in `phase.repos`, concatenated in that order into `<run dir>/handed/<actionId>.diff`. For each name, take the record of `repos` with that `name`. A run from an older release has one record with no `name`: use that record. Fetch the record's base, then diff from the merge base with it: `git -C <root> fetch origin <base>`, then `git -C <root> diff $(git -C <root> merge-base origin/<base> HEAD) HEAD`. Write the first repository's diff with `> <run dir>/handed/<actionId>.diff` and append each later one with `>>`. A run from an older release can have no `base`. For that run, the base is the default branch: the name after `origin/` that `git -C <root> symbolic-ref --short refs/remotes/origin/HEAD` prints.
2. Load `/<hostBinding.invoke>` with the Skill tool and follow its procedure in this thread, with the staged diff as its code-diff artifact. Before its first dispatch, check the installed review. The review plugin root is the folder above `runtime/` in the command path that the loaded skill names. Run `classes --class <the borrowed entry's classId> --installed <review plugin root>/<the entry's installedManifest>`. A mismatch is a stop. Skip its triage step. The runtime rules on the findings, not you or the person.
3. The review writes `bundle.json`, `result.json`, and `evidence.json` in its own run directory (its `runDir`). Then run `borrowed --ticket <ref> --action <actionId> --result <runDir>/result.json --evidence <runDir>/evidence.json --bundle <runDir>/bundle.json --scope branch`. Pass `--root <run store>` when this run uses a nondefault store. The CLI reads the saved Kiln host and staged diff for that pending action, then checks the Class, host, digest, and staged diff bytes. Write its `outcome` array, as JSON, to `<run dir>/handed/<actionId>-output.txt` and `{"modelBinding": {"model": "main-thread"}, "usage": <its usage>}` to `<run dir>/handed/<actionId>-meta.json`, and run `receipt`. Leave `toolCalls` out: the review's tool calls are not measured here, and an empty list would read as measured with none. Never triage the findings yourself.

## Terminal

When `next.terminal` is true, `next.status` names the end: `complete`, `abandoned`, or `gap`.

`complete`: the person said yes to the pull requests of the last phase. Open and record them by the pull request rules below, then close.

The pull request rules hold at a release stop and at `complete`. Check whether each repository of the phase is public: for each name in `show`'s `phase.repos`, take the `root` of its record in `show`'s `repos` (on a run from an older release, the one record) and run `gh repo view "$(git -C <root> remote get-url origin)" --json isPrivate -q .isPrivate`. If any prints `false`, run `pr --ticket <ref> --public`. If every one prints `true`, run `pr --ticket <ref>`. If one prints anything else, stop and say so. Never run `pr` without `--public` on an unknown visibility: on a public repo, that form puts the full text of each finding in the pull request body. One `--public` flag covers every block that the call writes. If `pr` refuses with `KILN_PR_KEY_MISSING`, show its message and stop. `pr` returns `pullRequests`, one entry per repository the phase wrote to, in plan order. For each entry, read `repo`, `worktree`, `branch`, `base`, `titlePath`, and `evidenceBlockPath`. Look for a pull request already on the branch: `gh pr view <branch> --repo "$(git -C <worktree> remote get-url origin)" --json url,state`. When it prints `no pull requests found` and exits non-zero, the branch has none. Push the branch: `git -C <worktree> push -u origin <branch>`. When the lookup's `state` is `OPEN`, an earlier phase opened that pull request and the push updates it: do not open another, and record its `url`. When the branch has none, or its `state` is `MERGED` or `CLOSED`, open a new pull request for that worktree's branch, with no `cd`, always with the entry's base: `gh pr create --repo "$(git -C <worktree> remote get-url origin)" --base <base> --head <branch> --title "$(cat <titlePath>)" --body-file <evidenceBlockPath>`. A run from an older release has no `base`. For that run, leave `--base` out, and the pull request targets the default branch. The branch name and the title follow the repository's own conventions, read by the finder at the start of the run. Pass the title through `$(cat <titlePath>)`, not `"<title>"` pasted in. A command substitution's output is not parsed again. The ticket author's raw text (a backtick, a `$(...)`, a `"`) reaches `gh` as one plain argument instead of expanding or breaking the command. The new pull request's URL is the last line it prints. Record each pull request, the open one or the new one: `pr-opened --ticket <ref> --repo <repo> --url <url>`. If push fails, inspect the remote branch before retrying. If pull request creation fails, look for an existing pull request on the same branch before retrying. Keep the person informed of a failure that needs a new decision.

At `complete`, after every pull request of the phase is open and recorded, run `close --ticket <ref>`. Close takes no link flag: it reads the links that `pr-opened` recorded. If close refuses with `KILN_PR_UNRECORDED`, record the pull request of the repository it names and run close again. Close writes the readout, and the readout carries every pull request link. Do not run `readout` after close, because it writes the readout again without the worktrees. On a markdown ticket, close adds every link under References inside the Context section. On a GitHub issue, a Jira ticket, or a plan or a decision document used as the ticket, close writes nothing to it. The pull request body names a GitHub issue, so the issue shows the pull request on its own. On a Jira ticket, the branch name or the title holds the ticket key, and Jira links the pull request by the key. Close removes each worktree that the run created once its tree is clean and its branch is pushed, and keeps every other worktree. Print the mode line, the member table, the floor line, the `pull request:` lines, the `review:` lines, the `## Worktrees` lines, and the unread places from the file at the `readoutPath` that close prints. The `## Worktrees` lines say which worktrees close removed and which it kept, and why. If the readout has a `ticket blocks not read` line, print it as it is. Nothing else: no merge.

`abandoned` or `gap`: run `readout --ticket <ref>`. Report the table and the stop that ended the run. Report any `pull request:` lines, the links an earlier release stop recorded, and any `ticket blocks not read` line from `readoutPath`. The run stays on its ticket key. When the person asks to restart an ended run, use `open --ticket <ref> --again`; for an approved plan, add `--approved-plan` and `--ticket-plan` as at the open step. `--again` can also replace an unbuilt discovery run of an approved plan. `open --again --approved-plan <absolute-plan-path> --ticket-plan <a task plan generated again>` on the same approved plan keeps each done task whose commit is on its branch; `open` returns them as `carried`, the build question marks them, and the run continues after them. A plain `open --again` opens discovery and carries nothing. The CLI keeps the earlier run readable under its returned `setAside` path. Do not replace a live run after build approval or code tasks: the CLI refuses with `KILN_RUN_NOT_ENDED`.

## Never

Never reorder, collapse, or skip an action. Never decide whether a second member runs. Never invent, drop, or relabel a finding or a ruling. Never open a pull request without the person's yes. Never write to a GitHub issue or Jira ticket except through `reply`. Never write an agent member's output file or meta file by hand: the measure script writes both. Never search for a repository outside the checkout folders.
