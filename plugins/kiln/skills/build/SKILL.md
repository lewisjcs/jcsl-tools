# Build

You are the build host. The approved plan gives the task scope. You choose safe execution details, then let the runtime route each action. You dispatch, measure, and record results. Do not implement a code task yourself. Do not change a member's outcome or skip a pending action.

## Preflight

- `node --version` is 22 or newer. CLI = `node "${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs"`. Never `cd`; pass absolute paths. A markdown ticket is always passed as its absolute path, the same path every session, because the run is keyed on it.
- `KILN_CHECKOUTS` names the folders that hold the repository checkouts, as absolute paths joined by `:`. The profile's `settings.json` sets it under `env`. If `KILN_CHECKOUTS` is unset, identify the checkout parent from the current workspace or plan. Set it for this command only. If no source identifies it, ask for the checkout location.
- Input: an absolute plan path or a ticket reference (`owner/repo#N`, an issue URL, a Jira key, or a markdown path). Send a new idea to kickoff for a plan. A Jira key is read in one of two ways, and this release never writes to Jira. If the setting `KILN_JIRA_VIEW` names a command, the runtime runs that command to read the ticket. The setting can also name a script of the person's own that prints one ticket as JSON. With no setting, the runtime reads the ticket through this session's Jira read tool, and it tells you when to call the tool: the refusal `KILN_JIRA_READ_NEEDED` lists ticket keys in `details.keys`. If the session lists that tool by name only, load it first. For each key, call the tool whose name ends in `getJiraIssue` once, with `issueIdOrKey` set to the key and `cloudId` set to the Jira site, and with no other input. A hook sets the other inputs and saves the answer for the runtime. The tool's result is then one line with no ticket text. That is correct: never call the tool again to see the ticket, and never write a ticket file yourself. To find the cloud id, call the tool of the same Jira server that lists the sites you can reach. If it lists more than one site, ask the person which site holds the ticket. If the call fails for one key, go on to the next key. After a `KILN_JIRA_READ_NEEDED` at `open`, run `open` again with the same flags. `open` can ask twice: once for the ticket and once for the tickets that it links to. After a `KILN_JIRA_READ_NEEDED` at a later command, run `next --ticket <ref>`. A command that already saved its state does not refuse for a read, and a command that only shows the run does not refuse either. The `next` of its answer then holds `jiraRead` in place of an action. Read the other fields of that answer as always. Then call the tool once for each key in `next.jiraRead.keys`, and run `next --ticket <ref>`. If the session has no tool whose name ends in `getJiraIssue`, show the refusal's message to the person and stop. For another `KILN_JIRA_` refusal, read the named capture and correct a safe tool or command setup error. Preserve an unreadable capture and report the limit. `KILN_JIRA_NOT_READ` means that no answer was saved: the session has no Jira read tool, the call failed, or the session started before the plugin update. `KILN_JIRA_CAPTURE` means that the saved answer cannot be used, and its message names the kept file. Never run a login for the person. After such a refusal on a later command, resume with `next --ticket <ref>`, not with the command that failed. If `next` names the action whose command failed, run that command again: a `receipt` with its files in `<run dir>/handed/`, a `reply` with the same text from the person. The optional `--base <branch>` names a stacked base. The old `--plan <path>` remains available for existing build calls.
- Before each Class dispatch, run `classes --class <classId> --installed <body-path>` for that Class. Use `${CLAUDE_PLUGIN_ROOT}/agents/<file name>` for an agent and `${CLAUDE_PLUGIN_ROOT}/skills/<folder>/SKILL.md` for a skill. Check the borrowed Class at its action below. Stop if an installed body differs from canon.
- A CLI error prints `{"error": {"code", "message", "details"}}` on stderr. Read its code and the saved run state. Fix a routine checkout or tool problem when you can do so without losing work, then retry the same pending action. Use `next --ticket <ref>` after an action already saved its state. Keep approval, write scope, and state integrity refusals in force. Never edit state.json or a member's measured output.

## Select the approved plan

If the input is a Jira key followed by its matching browse link in parentheses, use the key for every command.

If the input is a plan path, read its `Source ticket:` line. If the line contains a Jira key and its matching browse link, use the key. If the line says `none`, use the plan path. Otherwise, use the reference on that line.

If the input is a ticket reference, locate the current OS workspace project area. Search `projects/active/*/plans/` for `*.approval.json` files. Read each corresponding Markdown plan. Compare Jira keys after you remove a matching browse link from either reference. Compare other references exactly. If several plans match, ask the person to choose one. If none matches and the person asked to execute an approved plan, return to kickoff. For an ordinary ticket build without a plan, explain that Kiln will discover and plan the work first. Use `open --ticket <ref> [--base <branch>]`, then follow its `next` actions. Skip the approved plan sections below.

Run `plan-approval-check --file <absolute-plan-path>` on the selected plan. If it fails, return to kickoff. Read the plan's recommended build method and the tools available now. Explain a material method change before build approval.

If a saved approved build already holds `brief.tasks.plan`, compare its current sources with the approved scope. Then run `open --ticket <ref> --approved-plan <absolute-plan-path>` without `--ticket-plan`. The saved task contract stays in the run. Continue from the returned `next` action. Do not translate the plan again during resume. If the saved run still waits on discovery, prepare the direct route below and use `--again` before build approval.

## Prepare the approved build

Read the approved plan, its named ticket, material comments, named source hashes, and current repository facts. Compare them with the approved scope. If a change alters the outcome, acceptance, task scope, or a material premise, return to kickoff before opening a build run. Report an unread source and the resulting limit. Keep a cosmetic change visible. This is a focused preflight, not a new research or planning pass.

Find the repository under `KILN_CHECKOUTS`. Read its instructions and use `git worktree list --porcelain`, `git status --porcelain`, and `git diff` to identify a suitable branch. Reuse a clean worktree whose branch fits the plan. If none exists, create a branch and worktree from the selected base under the repository's conventions. Do not discard local changes. If several candidates remain, ask the person to choose between the named branches.

Translate the approved tasks into one `kiln:ticket-plan@1` JSON file outside plugin source. This is build setup, so do not dispatch Prospector, Designer, or Planner. Read `format/schemas/ticket-plan.schema.json` or an existing valid task plan for its fields. Set `ticketRef` to the command reference. Set `source.path` and `source.sha256` to the approved plan. Set each task ID, goal, acceptance coverage, dependency, and relative write path from the matching approved task. Cover every acceptance line. Choose `doneWhen` commands from the repository's actual test tools. Each command names the selected worktree and gives an observable expected result. Put absolute input paths, the worktree path, and its branch in each task. Do not expand the approved task's goal or file scope.

Run `plan-check --file <task-plan-path>`. Correct a contract or command shape error in the JSON file. If the approved plan cannot support a task mapping, return to kickoff. Then run `open --ticket <ref> --approved-plan <absolute-plan-path> --ticket-plan <task-plan-path> [--base <branch>]`. The runtime compares the tasks with the approved plan and checks the existing worktree before it creates a run. If an earlier run stopped before build approval and code tasks, add `--again`. The CLI moves its record aside and keeps it readable. Read `state.json` in the new run directory. Check its plan path, SHA-256, task order, and selected worktree.

The first action of this route is build approval. Show its question, worktree, task checks, and any ticket diff. Map clear consent to the runtime's `yes` reply. Save the original words beside that reply. If consent is unclear, ask a focused question. Do not invent consent.

If `KILN_APPROVED_TASK_CHANGED` reports a JSON mapping error, correct the mapping and retry `open`. Return a real scope change to kickoff. If `KILN_APPROVED_BASE` reports a missing `origin/HEAD`, run `git -C <checkout> remote set-head origin --auto`. Retry `open`. If the selected base is absent on the remote, choose a valid base within the plan and show it. If `KILN_APPROVED_WORKTREE_DIRTY` appears, preserve the changes. Find a clean checkout or resume the run that owns them. If a dependency is missing, use the repository's install command in the worktree. Resume with `next`. If `KILN_ACTION_STALE` appears, read `next` before acting. If measurement fails, inspect the worktree for writes and commits before a retry. Keep approval, state integrity, and measured write refusals in force.

## Open

For an approved plan, use `open --ticket <ref> --approved-plan <absolute-plan-path> --ticket-plan <task-plan-path> [--base <branch>]`. For an ordinary ticket without one, use `open --ticket <ref> [--base <branch>]`. The CLI fetches the ticket and its linked sources into the run directory. Read `fillState`, `roster`, and `next` from its result. If `resumed` is true, continue from the saved action.

For a request without an approved plan, the finder's discover step runs first. It finds the repository, base, branch, title, and ticket kind. Its unresolved gaps reach one question. The approved plan route above starts at build approval.

The run reads the ticket's own sections by name. Context, Background, Problem, or Description holds the intent. Functional Requirements or Acceptance Criteria holds the acceptance lines. Detailed Solution holds the approach. When the run fills a part and the ticket lacks its section, the run adds the section with the first name in that part's list. The facts and the tasks stay in the run and never go on the ticket.

## Approved plan drift

Before `open`, compare the current ticket, material comments, source hashes, and repository facts with the approved plan. If a premise or scope changed, return to kickoff. If a source is unreadable, name the evidence limit. State cosmetic changes before build approval. At build approval, the runtime reads the ticket again and rejects changed acceptance or plan bytes.

## The loop

Use `next` from each `open`, `receipt`, or `reply` result. Call `next --ticket <ref>` only when no result is in hand. Keep the run directory from `open` or `show --ticket <ref>`.

For an approved plan, build approval is the first action. After consent, dispatch Crafter for each task, then Inspector and the selected review. Ask for pull request consent at the runtime stop. For a request without an approved plan, follow the discover and planning actions that `next` returns.

**`hostBinding.kind` is `person`.** Read `next.questionPath` and show its question and detail. Show the exact diff before a ticket write. Show the selected worktree and checks before build consent. For clear consent in ordinary language, save the person's exact words to `<run dir>/handed/<actionId>-person.txt`, then pass `yes` to `reply`. Do not infer consent from a request to discuss or revise a plan. For a clear request to retry, revise, or abandon, map the words to the runtime reply and save the original text. If the requested action is unclear, ask one short question. Use the pending action ID. After a refused reply, read the new question before asking again. A person can reply `abandon` to end a run. A `retry <note>` after two failed member attempts keeps the existing write baseline. An approved scope change returns to kickoff.

**`hostBinding.kind` is `agent`.**
1. If `next.write` is present, `next.before` names the before file. If `next.before.take` is true, snapshot the tree first: `writes snapshot --repo <next.write.repoRoot> --out <next.before.path>`. If it is false, take no snapshot. The runtime measures a task's second attempt against the tree before the first attempt. It measures a retry after a second failure the same way, so no attempt hides what an earlier one left. A retry after a member's own gap, or a task after a `change`, starts a fresh measurement.
2. Dispatch exactly one Agent call: `subagent_type` = `hostBinding.agentType`, `model` mapped from `hostBinding.model` (`claude-sonnet-5` to `sonnet`, `claude-haiku-4-5` to `haiku`, `claude-opus-5` to `opus`), prompt = `next.promptBody` verbatim. It is one line that names the brief file at `next.briefPath`. Never paste the brief, the ticket, or repo content in yourself. Note the agentId the Agent result names.
3. Measure the dispatch with the host script: `node "${CLAUDE_PLUGIN_ROOT}/runtime/hosts/claude-code/bin/measure.mjs" --agent <agentId> --action <actionId> --run <run dir> --model <hostBinding.model>`. If `next.write` was present, add `--cli "${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs" --repo <next.write.repoRoot> --before <next.before.path>`. The script finds the dispatch transcript. It writes the member's reply, from the hand-back tool input, to `<run dir>/handed/<actionId>-output.txt`. It writes the usage, the tool calls, and the write measurement to `<run dir>/handed/<actionId>-meta.json`. It prints one line: print that line to the person. If it exits non-zero, it prints `{"error": {"code", "message", "details"}}` on stderr and writes nothing. Inspect its error and the worktree before a safe retry. `MEASURE_NO_HANDBACK` means the member ended without a reply. Never write the output file or the meta file by hand, and never record `outputTokens`.
4. `receipt --ticket <ref> --action <actionId> --output <the output file> --host-meta <the meta file>`. Read `ledger.outcome`, `runStatus`, `breach`, `omissions`, `issues`, `mode`, `installed`, and `next`. A `next` with `attempt` 2 is the runtime handing you the retry: dispatch it like any action. A `ledger.outcome` of `retries-exhausted` means the runtime refused the reply twice: `next` is then a question for the person. For `KILN_ACTION_STALE`, read `next` and use its pending action. For a `RUNTIME_*` refusal, preserve its evidence and follow the runtime retry. Stop on state tampering. `KILN_RUN_TERMINAL` means that the run has ended.

**`hostBinding.kind` is `skill`.** The designer plays in this thread and reads its brief from the file at `next.briefPath`. Invoke it with the Skill tool: `/<hostBinding.invoke> --ticket <ref> --cli ${CLAUDE_PLUGIN_ROOT}/runtime/bin/cli.mjs`. It writes `<run dir>/handed/<actionId>-output.txt` and `-meta.json`. Then run `receipt` with those two files.

**`hostBinding.kind` is `borrowed`.** A second review of the branch.
1. Stage the diff. `show --ticket <ref>` prints `repo` as `{checkout, root, branch, prTitle, base}`. Fetch the base, then diff from the merge base with it: `git -C <repo.root> fetch origin <repo.base>`, then `git -C <repo.root> diff $(git -C <repo.root> merge-base origin/<repo.base> HEAD) HEAD > <run dir>/handed/<actionId>.diff`. A run from an older release has no `repo.base`. For that run, the base is the default branch: the name after `origin/` that `git -C <repo.root> symbolic-ref --short refs/remotes/origin/HEAD` prints.
2. Load `/<hostBinding.invoke>` with the Skill tool and follow its procedure in this thread, with the staged diff as its code-diff artifact. Before its first dispatch, check the installed review. The review plugin root is the folder above `runtime/` in the command path that the loaded skill names. Run `classes --class <the borrowed entry's classId> --installed <review plugin root>/<the entry's installedManifest>`. A mismatch is a stop. Skip its triage step. The runtime rules on the findings, not you or the person.
3. The review writes `result.json` and `evidence.json` in its own run directory (its `runDir`). Then run `borrowed --result <runDir>/result.json --evidence <runDir>/evidence.json --scope branch`. Write its `outcome` array, as JSON, to `<run dir>/handed/<actionId>-output.txt` and `{"modelBinding": {"model": "main-thread"}, "usage": <its usage>}` to `<run dir>/handed/<actionId>-meta.json`, and run `receipt`. Leave `toolCalls` out: the review's tool calls are not measured here, and an empty list would read as measured with none. Never triage the findings yourself.

## Terminal

When `next.terminal` is true, `next.status` names the end: `complete`, `abandoned`, or `gap`.

`complete`: the person said yes to the pull request. Check if the repository is public: `gh repo view "$(git -C <repo.root> remote get-url origin)" --json isPrivate -q .isPrivate`. If it prints `false`, run `pr --ticket <ref> --public`. If it prints `true`, run `pr --ticket <ref>`. If it prints anything else, stop and say so. Never run `pr` without `--public` on an unknown visibility: on a public repo, that form puts the full text of each finding in the pull request body. If `pr` refuses with `KILN_PR_KEY_MISSING`, show its message and stop. Read `evidenceBlockPath`, `worktree`, `branch`, `base`, and `titlePath`. Push the branch: `git -C <worktree> push -u origin <branch>`. Open the pull request for that worktree's branch, with no `cd`, always with the run's base: `gh pr create --repo "$(git -C <worktree> remote get-url origin)" --base <base> --head <branch> --title "$(cat <titlePath>)" --body-file <evidenceBlockPath>`. A run from an older release has no `base`. For that run, leave `--base` out, and the pull request targets the default branch. The branch name and the title follow the repository's own conventions, read by the finder at the start of the run. Pass the title through `$(cat <titlePath>)`, not `"<title>"` pasted in. A command substitution's output is not parsed again. The ticket author's raw text (a backtick, a `$(...)`, a `"`) reaches `gh` as one plain argument instead of expanding or breaking the command. The pull request URL is the last line it prints. If push fails, inspect the remote branch before retrying. If pull request creation fails, look for an existing pull request on the same branch before retrying. Keep the person informed of a failure that needs a new decision. After the push and pull request creation succeed, run `close --ticket <ref> --pr-url <url>`. Close writes the readout, and the readout carries the pull request link. Do not run `readout` after close, because it writes the readout again without the link. On a markdown ticket, close adds the link under References inside the Context section. On a GitHub issue, a Jira ticket, or a plan or a decision document used as the ticket, close writes nothing to it. The pull request body names a GitHub issue, so the issue shows the pull request on its own. On a Jira ticket, the branch name or the title holds the ticket key, and Jira links the pull request by the key. Print the mode line, the member table, the floor line, and the unread places from the file at the `readoutPath` that close prints. If the readout has a `ticket blocks not read` line, print it as it is. Nothing else: no merge, no cleanup of the worktree.

`abandoned` or `gap`: run `readout --ticket <ref>`. Report the table and the stop that ended the run. Report any `ticket blocks not read` line from `readoutPath`. The run stays on its ticket key. When the person asks to restart an ended run, use `open --ticket <ref> --again`. For an approved plan, `--again` can also replace an unbuilt discovery run. The CLI keeps the earlier run readable under its returned `setAside` path. Do not replace a run after build approval or code tasks.

## Never

Never reorder, collapse, or skip an action. Never decide whether a second member runs. Never invent, drop, or relabel a finding or a ruling. Never open the pull request without the person's yes. Never write to a GitHub issue or Jira ticket except through `reply`. Never write an agent member's output file or meta file by hand: the measure script writes both. Never search for a repository outside the checkout folders.
