# README Ownership Classification

TL;DR: every section of an existing README carries exactly two values —
one ownership value and one freshness value — and those two values
together decide what the core may do to it. Only `cartographer-managed`
sections are ever written; everything else is preserved, proposed, or
reported.

This file is the sole definition site for the four ownership values and
the three freshness values, and the sole owner of the managed-section
marker grammar. Throughout, **section** means a section of the README
under analysis — a heading in that file and the lines beneath it — never
a section of this document or of any other file this plugin ships.

## Term Definitions

| Term | Axis | Definition |
|---|---|---|
| `human-authored` | ownership | A section written by a person, carrying no generator's marker and no Cartographer marker pair. |
| `cartographer-managed` | ownership | A section enclosed by a well-formed, matching Cartographer marker pair (see "Managed-section markers"). The core owns its body. |
| `other-tool-generated` | ownership | A section carrying another generator's marker or signature. Another tool owns its body. |
| `unknown` | ownership | The residual value: available evidence does not establish who wrote the section. Assigned when no other ownership branch fires, never inferred into a stronger value. |
| `current` | freshness | Collected evidence contradicts none of the section's claims. A named default added here so the freshness axis is exhaustive; it is not an additional classification drawn from the requirement. |
| `stale` | freshness | The section's subject still exists in the repository, and collected evidence contradicts at least one of the section's claims. |
| `obsolete` | freshness | The section's subject no longer exists in the repository, so the section describes something that is gone rather than something that changed. |

Ownership and freshness are independent axes. Each is exhaustive and
mutually exclusive **within itself**: a section carries exactly one
ownership value and exactly one freshness value. No exclusivity holds
*across* the axes — "a stale human-authored section" is
`ownership=human-authored` plus `freshness=stale`, a legal and expected
combination that needs no precedence rule.

## Classifying ownership

Apply in order, once per section:

1. A well-formed Cartographer marker pair encloses the section →
   `cartographer-managed`.
2. Otherwise, the section carries another generator's marker, signature
   line, or "generated by" header → `other-tool-generated`.
3. Otherwise, the repository's own history attributes the section's lines
   to commits carrying no generator signature → `human-authored`.
4. Otherwise → `unknown`.

Non-firing branches:

- A malformed marker pair does not reach branch 1. Mismatched start and
  end ids, a duplicate id within one README, a start with no end, an end
  with no start, or a nested start all mean branch 1 does not fire; the
  section falls through to the branch that does, and `unknown` is the
  usual result.
- Prose that merely mentions Cartographer does not make a section
  `cartographer-managed`. Only the marker pair does.
- Branch 4 is a stop, not a guess. A section the evidence cannot place is
  `unknown`, never assigned `human-authored` because that is the safer
  default — the safety lives in what `unknown` authorizes, below.

## Classifying freshness

Apply in order, once per section:

1. The section's subject is absent from the repository → `obsolete`.
2. Otherwise, collected evidence contradicts at least one claim in the
   section → `stale`.
3. Otherwise → `current`.

Non-firing branch, stated explicitly: branch 3 also catches the section
whose claims collected evidence neither supports nor contradicts. Such a
section is `current` **and is recorded as unassessed**, and the run
reports it as unassessed rather than as verified. `core/refresh.md`
defines the run's reporting semantics on top of that distinction: this
branch-3 record is the one that lands in its **not assessed** bucket by
evidence being collected and silent, distinct from a carried-forward
section that lands in the same bucket by never being assessed at all.

## Action matrix

Rows are ownership values, columns are freshness values. All twelve
combinations are actioned; a combination absent from a caller's
expectations is still one of these twelve.

| ownership \ freshness | current | stale | obsolete |
|---|---|---|---|
| human-authored | Preserve unchanged. Emit no patch entry, and emit no proposal — an unchanged, uncontradicted section is not a finding. | Emit a proposed diff citing the contradicting evidence. Never overwrite the section, in fix mode or out of it. | Emit a proposed removal citing the evidence that the subject is gone. Never delete the section. |
| cartographer-managed | Redraft the body; if the redraft is byte-identical to the current body, emit no patch entry. Never rewrite a managed section to change wording alone. | Replace the body in place, between the existing marker pair, citing the contradicting evidence. Never append a second section with competing content. | Remove the whole managed block, marker pair included, and report the removal. Never leave an orphan start or end marker behind. |
| other-tool-generated | Preserve unchanged. Never wrap it in a Cartographer marker pair — wrapping would claim ownership the core does not have. | Report the contradiction with its evidence and emit no patch entry. Regeneration belongs to the owning tool, not to the core. | Report it as a removal candidate for the owning tool. Never remove it. |
| unknown | Preserve unchanged and report the ownership as unresolved. Fix mode does not reach it. | Preserve, emit a proposed diff citing the contradicting evidence, and report the ownership as unresolved. Never apply the proposal. | Preserve, report it as a removal candidate with the evidence that the subject is gone, and report the ownership as unresolved. Never remove it. |

Two shapes run through the matrix. The core **writes** only the
`cartographer-managed` row. For every other row it either preserves the
section untouched or emits a proposal a person decides on, and a proposal
is a report entry, never an edit.

Consequence and failure branch: a patch that modifies, removes, or
re-wraps any section whose ownership value is not `cartographer-managed`
is a contract violation. The core shall not report such a patch ready; it
reports the offending section and its classification instead.

## What `unknown` authorizes

`unknown` authorizes reporting, and nothing else. An `unknown` section is
never written, never removed, never wrapped in a marker pair, and never
reclassified to a stronger ownership value because a later stage needs to
edit it. The only path out of `unknown` is new evidence at the next
classification, not an editing convenience.

This is why branch 4 above may stop at `unknown` without a fallback:
`unknown` is already the most conservative outcome the matrix offers, and
guessing `human-authored` instead would gain nothing and lose the honest
report that ownership was not established.

## Preservation and fix mode

- Human-authored sections are preserved by default during any patch
  operation. "By default" means: with no caller instruction on the
  subject, the section is not modified.
- A `human-authored` section whose freshness is `stale` produces a
  proposed diff plus the evidence citation behind it, never a silent
  overwrite. The proposal is reported; applying it is a person's decision.
- Explicit fix mode, authorized by the caller, updates **only** sections
  whose ownership is `cartographer-managed`. Fix mode changes nothing
  about the other nine cells: they behave exactly as they do without it.
- A `cartographer-managed` section whose freshness is `stale` is replaced
  in place, never appended as a competing duplicate.

Consequence and failure branch: if fix mode is requested and no section
is classified `cartographer-managed`, the core produces no patch and
reports that there was nothing in scope. It does not widen its scope to
have something to fix.

## Managed-section markers

A `cartographer-managed` section is delimited by exactly this pair, one
marker per line, the start above the section's heading and the end after
its last line:

```markdown
<!-- cartographer:managed:start <id> -->
<!-- cartographer:managed:end <id> -->
```

`<id>` rules, defined here and nowhere else:

| Rule | Requirement |
|---|---|
| derivation | The kebab-case slug of the section's heading text. |
| format | Matches `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 characters. |
| uniqueness | Unique within a single README. |
| matching | The `start` id and the `end` id are byte-identical. |
| nesting | A managed block never contains another `cartographer:managed:start`. |

**Four of the five `<id>` rules are mechanically enforced.** The format,
uniqueness, matching, and nesting rules are enforced by
`core/local-validation.md`'s gate (d), `RULE` `marker`. `derivation` is
not mechanically checked, and that residual gap is stated here so it
stays visible rather than assumed closed.

The grammar has a consequence independent of the gate, because
classification reads it: a marker pair that violates any rule above is
not well-formed, so ownership branch 1 does not fire and the section
classifies as `unknown`. The gate reports the violation, and
classification still costs the section its managed status — a malformed
block is preserved and reported, never patched.

Note that the managed-section family and the evidentiary marker family
(`see:` and `rationale:`, defined in
`core/knowledge/evidentiary-marker-conventions.md`) are unrelated. They
share the HTML-comment shape and nothing else; no rule of either family
applies to the other.

## Verification check

Before a README patch is reported ready, confirm every one of these, and
report the first that fails instead of the patch:

1. Every section in the README under analysis carries one ownership value
   and one freshness value.
2. Every section the patch modifies or removes is classified
   `cartographer-managed`.
3. Every proposal the run emits for a non-`cartographer-managed` section
   appears in the report and not in the patch.
4. Every marker the patch writes satisfies the `<id>` rules above, and
   every managed block the patch writes has a matching start and end.
